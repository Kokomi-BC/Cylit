# Fine-grained Semantic Unit：设计（④⑤）

> 状态：**设计已定，实现中**（`chunk_type="unit"` 建进 LanceDB；检索 Top-K 以 unit 为主候选；
> 上下文 ±1 Small-to-Big）。相关代码：`backend/services/knowledge/chunking.py`（单元层）、
> `knowledge_service.py`（索引层）、`retrieval.py`（候选集）、`rag_service.py`（上下文扩展）。
> 数据依据见 `docs/dev-log.md` §17.63/§17.64 与 `scripts/kb_anchor_effect.py`。

---

## 0. 一句话

现在 chunk 是**检索单元兼上下文单元**（1400 字，装 5~7 个段落），于是 LLM 标的语义边界
有四到六成被长度约束合并掉。改成两层：

```
LLM 只回答"哪里是语义边界"          ← 分组（grouping），不生成任何文字
代码从页级行里取原文拼出 unit        ← 取原文（grounding），与 chunk 同一批行
unit  = 检索单元（细，中位 2 行 ≈ 300~500 字）
chunk = 上下文单元（粗，≈1400 字，**由整数个 unit 组成**）
```

## 1. 为什么 unit 必须同时是 chunk 的原子

`unit` 是"检索单位"，`chunk` 是"喂给 LLM 的上下文单位"。如果 chunk 的边界可以落在 unit 内部，
一个 unit 就会有两个父 chunk，small-to-big 该往上取谁就没有确定答案。所以定一条硬约束：

> **chunk = 连续的整数个 unit**（unit 是分块层的原子，`assemble` 只在 unit 边界上下刀）。

代价是 chunk 长度不再贴着 target（会偏大一点）；收益是三层关系都是确定的：
`row ⊆ unit ⊆ chunk`，每一层都能断言"覆盖恰好一次"。

## 2. unit 从哪来（④）

```
unit 边界 = LLM 语义锚点 ∪ TOC 节点边界 ∪ unit 硬上限（长度兜底）
```

| 边界来源 | 谁决定 | 说明 |
|---|---|---|
| `semantic_break` 行 | **LLM**（转录时给的 `breaks`，见 page_translate） | 细粒度语义分组：定义→定义、方法→实验、一段推导→下一段推导… |
| TOC 节点边界 | 阅读器目录 | 小节之间永不合并（宏观边界，LLM 不许改） |
| `unit_max_chars`（默认 700） | **代码** | 兜底：某节里 LLM 没标锚点时，一段很长的正文不能整节变成一个 unit；到上限就在**行边界**切（行=段落，永不切进公式/表格/句子） |

测得的现状（`scripts/kb_anchor_effect.py`）：turbo 69 个单元 / 每单元中位 **2 行**（p90 5、max 14），
attention 42 个 / 中位 2 行 —— LLM 的锚点已经足够细，**这一层不需要重跑视觉模型**。

## 3. 单元对象（代码取原文，绝不由 LLM 生成）

```python
row_ids        # 组成它的行（顺序即文档序）
en / zh        # "…".join(row.original) / "…".join(row.translation) —— 逐行拼装
section_path, section_kind
parent_chunk_id, unit_index, unit_count      # 与 chunk 的关系
prev_unit_id, next_unit_id                   # ±1 邻居（检索侧直接用，不必现算）
anchor_used: bool                            # 这条单元的左边界是不是 LLM 锚点
pages, chars
```

`unit_id = "{paper}:unit:{first_row_id}"`（不再是位置编号，重译后仍可重新落回行）。

## 4. 索引（⑥）

- 与 chunk 进**同一张 LanceDB 表**，`chunk_type="unit"`，语言行 `:zh` / `:en`（与 text 同规则）；
- 元数据里带 `parent_chunk_id` / `prev_unit_id` / `next_unit_id` / `row_ids` / `section_path`；
- **公式 / 图 / 表原子 chunk 不变**（它们本来就是细粒度、不可切的）；
- 规模预估：turbo 69 unit（+138 行）、attention 42（+84 行）→ 全库 267 → **489 行**；
  重建索引时 embedding 多花约 220 次（本地/远端 embedding 都是秒级）。

## 5. 检索（⑦）

```
候选集 = unit, formula, figure, table          # 正文 chunk 不进候选
```

理由：正文 chunk 与它的 unit 是**同一批行的两种粒度**，都进候选就会出现"同一段内容两条命中"，
Top-K 被自己挤掉、重排还要替同一内容排两次序。

- setting `kb.retrieval_types`（默认 `unit,formula,figure,table`）；
- **空结果兜底**：候选集过滤后一条都没有（老索引、或 unit 未建）→ 自动用全部类型重搜一次，
  行为与改造前一致（不因为没建 unit 就检不到东西）；
- 浏览接口（`/knowledge/chunks`）默认**不列 unit**（那是"逐块读论文"的视图，多一层粒度只是噪声）；
  `overview` 会单列 unit 计数。

## 6. Small-to-Big（⑧）

命中 unit 之后往上取上下文，`kb.unit_expand` 三档：

| 值 | 上下文 |
|---|---|
| `0` | 只有命中的 unit（≈300~500 字） |
| `1`（默认） | **命中 unit + 前后各 1 个 unit**（同父 chunk 内，不跨节） |
| `2` | 整条父 chunk（≈1400 字） |

规则：

- **只在本 unit 所属的父 chunk 内扩**（不跨父、不跨节）；父 chunk 边界天然就是这条单元的
  文本上下文边界；
- **按父 chunk 去重**：两条命中落在同一父里 → 合并成一个来源（取并集），
  否则同一段内容会在 `[S1]`、`[S3]` 里各出现一次，白烧上下文预算；
- **预算**：沿用 `build_context` 的 `max_chars`（默认值见代码），扩展后的块超预算就退到
  只给命中 unit（保证"命中内容一定在上下文里"优先于"给它补邻居"）；
- 来源里记 `expanded_units` 与 `expand_mode`，便于回归时量"扩展带来的字符成本"。

## 7. 校验与回归（⑨）

实现后的不变量（进 `chunking.validate`，`units` 传入才查）：

1. **单元分片**：单元按行序**恰好一次**覆盖同一批"该进正文的行"；
2. **父子确定**：每条单元恰好被 1 条 chunk 认领（`chunk.unit_ids`），且它的行全在该 chunk 内；
3. **邻居**：`prev/next` 指向同一父 chunk 内的相邻单元（首尾为 `None`）；
4. **上限**：单元 ≤ `unit_max_chars`（只由一行组成的单元除外 —— 单行不可切）。

### 实测（两篇论文，30 题固定回归）

索引规模：turbo 425 行（正文 88 / **单元 236** / 公式 89 / 图 10 / 表 2，v57）、
attention 192 行（正文 46 / **单元 116** / 图 10 / 公式 12 / 表 8，v52）—— 合计 267 → **617 行**。
单元粒度：turbo 118 条（en 中位 **546 字**，LLM 锚点切出 64 条、长度兜底 49 条），attention 58 条（中位 464）。

| 指标 | arm3b 只索引正文 chunk | arm4 单元检索 + ±1 |
|---|---|---|
| hit@6 / 正文命中 | 100% / 97% | 100% / **97%** |
| MRR / 正文 MRR | **0.9778** / **0.9011** | 0.9667 / 0.8889 |
| **命中块长度中位** | 778 字 | **300 字**（−61%） |
| **上下文字符中位**（6 条来源） | 6057 | **5166**（−15%） |
| 首次命中类型 | text 27 / table 2 / figure 1 | **unit 25** / table 3 / formula 1 / figure 1 |
| 公式上下文（语义块含公式） | 90% | 80% |
| 逐题（30 题） | — | 更好 3（q19 3→2、q24 2→1、q29 5→3）、更差 2（q08 1→2、q15 1→3）、丢失 0 |

**结论**：细粒度目标达成（命中块 778 → 300 字），上下文反而更省（6057 → 5166，因为 ±1 单元比整块小），
hit@6 不变；代价是正文 MRR −0.012（3 题更好 / 2 题更差）。这是**粒度与精度的交换**，
不是"更准"：单元让"命中的就是那一段"成立，但重排在更细的候选上偶尔挑错。

### 已知的下一步

- **候选池按粒度重调**：`rag_top_k_vector / lexical / fused / rerank` 是给 1400 字块调的；
  单元更短更多，值得把前两级放宽（例如 vector 30 → 60）。
- **`±1` 的边界**：目前 ±1 只在同一父 chunk 内扩（不跨节）。跨节扩会让上下文带上邻节的句子，
  要不要放开取决于"问题是否常常跨节"。
- **单元长度兜底 700**：turbo 118 条里 49 条是兜底切出来的（不是 LLM 边界）。若要更纯的语义单元，
  下一步该让模型在长节里多标几条锚点（提示词里给出"这一节目前只有 1 条边界"的反馈），而不是把 cap 调小。
