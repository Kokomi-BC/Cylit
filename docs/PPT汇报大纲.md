# Cylit 论文理解系统 · PPT 汇报大纲

> 问题驱动的技术讲解 · 建议时长 **9–10 分钟** · 共 14 页
>
> **汇报主线**：遇到一个实际问题 → 尝试解决 → 发现新问题 → 逐步增加提示词、程序规则和校验机制 → 形成完整系统。

> 一句话定位：Cylit 不只是把论文翻译成中文，而是把论文转化为**可阅读、可理解、可检索、可追溯**的知识。

# 第一部分 · 让机器读懂论文

## 第 1 页｜项目背景：读论文的三个实际问题

**页面内容**

- 英文论文阅读速度慢，逐句精读耗时。
- PDF 只能阅读，难以直接检索和提问。
- 读完后难以回忆，也难以跨论文寻找相关方法。

**项目目标**：把论文转化为可阅读、可理解、可检索、可追溯的知识。

**讲解重点**

不先罗列技术栈，先说明系统为什么有必要做。

---

## 第 2 页｜问题一：PDF 不是机器能直接理解的数据

**问题**

PDF 保存的是排版结果，不是结构信息：它只记录"哪个字画在哪个坐标"，不知道哪段是标题、哪段是正文、双栏该先读哪一栏。

**解决过程**

1. 提取文字、位置与结构信息（文字层、矢量层、位图层）。
2. 识别标题、正文、公式、图片、表格和参考文献。
3. 按正确的阅读顺序组织内容，保留图表与正文的关系。
4. 对扫描版 PDF，补充视觉模型转录路径。

**页面建议**

一张"原始 PDF → 结构化内容"的前后对比图。

**本页结论**

先把论文从"印刷品"变成后续程序可以处理的数据。

---

## 第 3 页｜问题二：如何让大模型既转录原文，又生成中文译文？

**问题**

直接让模型翻译，不一定能纠正解析错误；原文和译文分开生成，又会带来段落对应问题。

**解决过程**

1. 要求模型**忠实转录英文**，保留公式、表格和图注。
2. 增加**中文翻译**任务，要求术语和表达全文一致。
3. 明确**输出格式与结构边界**，让结果能被程序继续处理。
4. 最终采用一次调用同时产出两份内容，两者段落天然一一对应。

**页面建议**

"输入内容（页图 + 页内文本）→ 提示词约束 → 英文转录 / 中文翻译 → 阅读器对照"的流程图。

**讲解重点**

不要只说"调用大模型翻译"，要说明为了让输出**可用**，逐步增加了哪些任务要求和结构约束。

**本页结论**

一次生成两份产物，省掉了整类"事后对齐"的难题。

---

## 第 4 页｜问题三：转录和翻译，为什么分成两条路并行做？

**问题**

一页论文要做两件事：把页面上显示的内容照抄成英文，再翻成中文。
排队做的话，22 页要花约 15 分钟，其中大半时间只有一条路在干活。

**解决过程**

1. 最初让**一次调用**同时产出原文和译文。能用，但两件事的提示词、术语表、产物文件、下游用法都不同，混在一起既互相牵制，也放弃了并行的可能。
2. 拆成两个独立任务：**英文转录**、**中文翻译**。各自有独立的前文、独立的缓存前缀、独立的产物文件。
3. 但每条路内部仍然**一页一页串行**——第 N 页要能看到前面所有页的完整上下文，前缀缓存才命中。
4. 两条路各占一个工作线程，第三个线程留给解析和索引。

**页面建议**

一张时间轴并列图（用真实数据，不要用虚构时间）：

```
串行    A 转录 373s ███████████
                          B 翻译 551s █████████████████
                            合计 924s

并行    A 转录 373s ███████████
        B 翻译 551s █████████████████
        墙钟    552s █████████████████
```

**讲解重点**

- "并行"指的是**两条流水线之间**并行，不是一条流水线里所有页并行。
- 省下的不是模型算得快，而是短的那条路完全不用排队。

**本页结论**

把两件职责不同的事拆开，既让它们同时跑，也让各自的提示词和产物互不干扰。

---

## 第 5 页｜问题四：两条路各自切段，怎么保证每行都对得齐？

**问题**

两路都对同一页做分段判断，但依据不同、语言不同，同一页经常差 1～2 段。
块数相同时按序号配没问题；块数不同时，**"多出来的那段该插在哪"程序算不出来**——只能猜，猜错就把这一页后面每一行都错开一位。

**解决过程（三次迭代）**

**第一步：按序号或按结构猜着配。**
冒出两个问题：一页错位，整页后面全错；页首两个同级标题长得一样，实测会把英文标题配到中文摘要上。

**第二步：给两侧一份共同的"原文块号"**，让模型在输出里声明"我这一块覆盖了哪几个原始块"。
程序校验四条：项数相等、块号必须是本页的、合起来不重不漏、顺序一致。
全过才用它配对；**任何一条不过，整页退回上一版的保守做法**。
于是"一侧并成一块、另一侧拆成两块"能表示成一行。

**第三步（当前默认）：干脆让 A 先定块，B 照着 A 的块清单逐块翻译。**
对齐从"事后核对"变成"生成时就约定好"——只要求块数相等，不用再猜。
块数被模型改了，仍然退回上一版。

**页面建议**

三栏并列，同一段原文：

```
① 硬配        A: [第一段+第二段]      B: [第一段] [第二段]     → 后面全错位
② 共享块号    A 申报 b03|b04          B 申报 b03, b04          → 合成一行
③ 生成时约定  A 先定 2 块，B 逐块回 2 块                        → 天然一一对应
```

**讲解重点**

- 不是一开始就设计出契约，而是：先跑起来 → 发现错位 → 加坐标 → 加校验和回退 → 最后发现**让上游把结构定死，比让下游猜得准更省事**。
- 两路的语义边界本来就允许不同（一个划英文、一个划中文），契约**不追求两边切得一样**，只保证对得回原文。

**本页结论**

模型负责语义判断，程序负责结构约束；对不上就退回保守方案，绝不假装对齐。

# 第二部分 · 让论文可以被检索和引用

## 第 6 页｜问题五：翻译完成后，为什么还需要 RAG？

**问题**

读完一篇论文，不代表能回答"我的文献库里还有哪些论文研究过类似问题"。

**解决过程**

1. 把论文内容保存为**可以重复利用**的知识。
2. 用户提问时，先从论文库**检索**相关内容。
3. 把检索到的原文片段交给大模型组织答案。
4. 保留来源信息，让用户能回到原文核对。

**页面核心流程**

```
用户提出问题 → 从论文库检索相关内容 → 大模型依据材料作答 → 答案附带来源
```

**本页结论**

RAG 的核心不是让模型记住所有论文，而是让它回答问题前**先找到相关证据**。

---

## 第 7 页｜问题六：论文应该切成多大的块，才能检索准确？

**问题**

整篇论文太长，整页内容又可能包含大量无关信息；检索单位不合适，直接影响回答质量。

**方案比较**

| 方案 | 问题 |
|---|---|
| 按固定字数切 | 可能截断句子、公式或论证 |
| 按自然段切 | 段落长度差异大，检索粒度不稳定 |
| 按章节切 | 结构清晰，但章节可能太长 |
| 按语义边界切 | 更关注"是否完整表达了一个意思" |

**设计选择**

利用论文理解过程中**已经获得的语义信息**辅助确定边界，同时用**程序规则**控制实际分块。

**页面建议**

先展示固定长度切分如何截断论证，再展示语义分块的结果。

**本页结论**

分块不是把文字切碎，而是确定后续检索和引用的**基本单位**。

---

## 第 8 页｜如何逐步完善提示词：让模型提供语义边界

**第一步：完成基本任务**
要求模型转录、翻译论文内容，获得可处理的文本。

**第二步：增加语义判断任务**
要求模型判断哪些位置适合作为新的语义单元起点，并输出边界标记。

**第三步：明确模型的职责边界**
模型只判断语义边界，**不直接决定最终块的大小**，也不负责保证所有结构约束。

**第四步：增加程序校验与回退**
代码检查行覆盖、顺序、章节边界和公式表格完整性；不满足要求时回退到更保守的行边界。

**讲解重点**

不是一开始就写出"万能提示词"，而是先实现基本功能，再根据下游检索需求增加语义标记，最后用程序规则补足模型无法稳定保证的约束。

---

## 第 9 页｜问题七：模型给出边界标记后，如何变成可靠的检索块？

**问题**

模型能判断语义，但输出仍可能遗漏边界、边界不合理，或破坏结构。

**解决过程**

1. 以结构化内容中的**"行"**作为最小单位，不直接切开一行。
2. 结合模型给出的语义边界，组合成合适大小的文本块。
3. 用论文目录限制**跨章节合并**。
4. 检查行是否完整覆盖、顺序是否正确、公式和表格是否完整。
5. 校验失败时**回退**到更保守的切分方式。

**页面建议**

"语义边界标记 → 分块程序 → 校验 → 合格的 Chunk / 回退"的流程图。

**设计原则**

**模型负责判断语义；程序负责组织结构、执行约束和检查结果。**

---

## 第 10 页｜问题八：切好的文本，怎样才能按"意思"检索？

**问题**

有了语义块之后，计算机仍需要一种可用于相似度计算的表示方式。

**解决过程**

1. 把每个文本块交给 **Embedding 模型**。
2. 将文本转换为**向量表示**。
3. 把向量、原始内容和来源元数据一起存入向量数据库。
4. 检索时把用户问题也转成向量，寻找语义相近的内容。

**要说明的三点**

- Embedding 不是翻译模型，它把文本映射为向量，让系统能用**相似度**找相关内容。
- 比起只匹配关键词，语义检索有机会匹配不同表述（例如"向量压缩的精度损失"与"量化误差"）。
- 本系统用**云端 Embedding 模型**（通过 API 调用），避免本地部署和维护推理服务。

**讲解重点**

Embedding 负责**初步召回**，不直接生成答案。

---

## 第 11 页｜问题九：只靠向量相似度，能否保证检索结果正确？

**问题**

语义相似不等于能回答问题；模型名、公式编号、数字这类内容也可能无法只靠语义稳定命中。

**解决过程（五步，横向流程）**

```
两路召回 → 结果融合 → 相关性重排 → 生成答案 → 引用校验
```

1. **两路召回**：向量检索负责语义相近的内容，词法检索负责关键词精确匹配。
2. **结果融合**：两种检索的分数不可比，只综合它们的**排名**。
3. **相关性重排（Rerank）**：把问题和每个候选**放在一起逐条判断**，重新排序，只留前几名。
4. **生成答案**：把筛选后的材料交给大模型，要求依据材料作答。
5. **引用校验**：检查答案中的说法能否对上检索材料；证据不足时明确说明，不强行作答。

**为什么召回后还要重排**

向量召回的目标是"找出可能相关的候选"，但"语义相似"不等于"最能回答这个问题"。
重排多花一点算力，换来的是交给大模型的材料更干净。

**页面建议**

五步横向流程图。若界面能展示重排前后的顺序变化，用**真实结果**；没有就只讲机制，**不要虚构效果对比**。

**本页结论**

检索结果不是越多越好，关键是让最终交给模型的证据尽量相关、可核对。

# 第三部分 · 让结果可信、真正可用

## 第 12 页｜进一步解决：如何让整篇论文的理解也能追溯来源？

**问题**

翻译解决了逐句阅读，但用户仍需要快速了解一篇论文的研究问题、方法、创新点和结论。

**解决过程**

1. 在翻译和分块之后，**单独启动**论文精读任务。
2. 为论文理解设计**独立提示词**，不把翻译与理解混成同一项任务。
3. 要求模型总结研究背景、问题、动机、创新点、方法、实验和局限。
4. 为可引用的内容提供 **Chunk 短码**。
5. 程序校验短码是否存在，并映射回真实来源。

**讲解重点**

引用校验可以发现**无效引用**，但**不能保证**每个观点在语义上都绝对正确。

---

## 第 13 页｜实际演示：从一个问题到原文证据

**演示顺序**

1. 打开论文阅读器，展示原文、译文和结构化公式、图表。
2. 打开知识库，展示已切分的 Chunk 和来源信息。
3. 输入一个需要跨论文比较的问题，例如："不同论文分别采用了什么方法解决相似问题？"
4. 展示检索结果、相关论文及具体内容。
5. 打开生成答案中的引用，回到对应原文核对。
6. 如果时间允许，再展示单篇论文的精读结果及其来源短码。

**演示重点**

用实际结果证明整条链路是**连通的**，而不是只展示界面或长篇总结。

**注意事项**

检索到相似内容，不代表两篇论文的方法相同，也不代表可以互相引用；仍需回到原文确认具体贡献与差异。

---

## 第 14 页｜总结：整个系统是如何一步步解决问题的？

**原则一：先解决数据问题，再解决理解问题**
把 PDF 转成结构化内容，才有可靠的下游处理基础。

**原则二：逐步增加提示词，再用代码规则兜底**
模型负责语义判断和内容生成；程序负责结构约束、校验与来源映射。

**原则三：从单篇阅读走向跨论文检索**
通过语义分块、向量索引、混合检索和引用校验，让论文内容可复用、可追溯。

**项目总结**

Cylit 不只是把论文翻译成中文，而是把论文转化为可以检索、理解和追溯的知识。

## 附录 B · 讲之前必须守住的边界（别多说，各一句）

1. **第 4 页的 924 秒不是实测的串行基线**，是"两路实测耗时相加"推算出来的。可以说"墙钟约等于较慢的那一路"，**不要说"提速 1.67 倍"**。
2. **第 5 页的契约不保证两路切分相同**，也不保证模型的语义判断正确；它只保证"对得上原文位置"和"对不上就退回"。
3. **重排不宣称准确率提升**；没有真实前后对比就不展示效果对比。
4. **引用校验不等于消除幻觉**；它只检查引用是否对应真实材料。
5. **Embedding / Rerank 的具体模型 ID**要在汇报前从配置或调用代码核实一遍（详见附录 C）。
