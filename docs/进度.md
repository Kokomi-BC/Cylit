### 2.2 翻译（产线 A，规划 §15 / §21.3）—— **页级翻译（唯一粒度：一页一次调用）**

- **一页一次调用**：输入 = 该页**页图（PNG，150dpi）** + 解析器抽出的页内文本 + 稳定前缀
  （文档简报 + 术语表 + **全文标题骨架**）+ **完整前文历史**（第 1..N-1 页原文+译文，见 §15）；
  输出 = 一个 JSON `{original_md, translation_md}`，即**两份互相独立、
  块划分一一对应的 Markdown**（原文是模型的忠实转录 / OCR，译文是中文翻译）。
- **标题层级有权威参照**：`【全文标题骨架】`列出整篇“编号 → 层级”的映射（`# 1 …` / `## 1.1 …`），
  它对整篇字节不变、放在稳定前缀里（前缀缓存仍然命中）；骨架里没有的标题按编号深度推断。
  以前靠模型逐页自己猜，同一层级在不同页会拿到不同 `#` 深度（详见 §15）。
- **完整前文历史（连贯记忆）**：每页 prompt 在稳定前缀**之后**逐页附上第 1..N-1 页的原文 + 译文
  （升序、模板逐字相同、表头不带页码），因此前文全部命**前缀缓存**；并发调度下只取"紧邻且连续完成"
  的那一串页（遇缺口就停，避免错位拼接）。目标模型窗口 1M token，实测演示论文整篇历史 13.2 万字 →
  默认上限 200 万字只是护栏，正常论文不截断。
- **对齐天然成立**：两侧同一套纯结构切块 → 块数相同就按序号对应（`align=exact`），
  块数不同才用 `difflib` 序列对齐（`align=structure`，块不丢），两侧都空是 `align=empty`。
  没有锚点、没有保序 DP、没有回退补译（`page_aligner` 已删除）。
- **完全信任模型**：不做校验、不做回退补译；图注不再单独调用，公式不再特殊处理，
  参考文献由模型原样保留（不翻译）。
- **思考模式兜底**：正文为空时按阶梯升档 `max_tokens`（8192 → 16384 → 32768 → 65536）重试，
  统计 `max_tokens_escalations`。
- **跨页衔接（页尾断词 / 续句）**：模型一次只看一页，页尾的断词、断句天然会出错。三道防线：
  ① **输入侧看 ahead**——prompt 在【本页】之后附【下一页开头】（仅 6 行 / ≤1200 字，明标"仅供衔接参考、不得收录"）；
  ② **提示侧三条硬规则**——译文不得出现断词连字符（`communication bot-` + `tlenecks` 必须在页内还原成完整词）、
  续句必须是完整句且不得以「……」或「（承接上页）」开头、看 ahead 内容不得转录进本页；
  ③ **读取侧兑底**——`reader_service.page_translations()` 在**读时**调 `page_continuity()` + `mark_rows_continuity()`：
  给跨越页边的行打 `continued_from_prev` / `continues` 标记，并清掉译文里残留的「……」开头
  与行尾连字符。**写在读时而不是写时**，所以旧产物不用重译也能自然受益（详见 §17）。
- **前端随之提示**：行标 `continues` 且下行标 `continued_from_prev` 时，该行译文显示「续下页」（
  此时复制按钮隐藏）；翻译任务进行中，尚未出译文的行显示「**等待翻译**」而不是「未翻译」（见 §17）。
- **文档简报**：每篇 1 次调用固化领域与统一术语，可人工编辑（`md/translation_brief.json`）。
- **产物 `md/pages.json`（翻译的唯一事实源）**：逐页 `{page, page_total, original_md,
  translation_md, rows[], align, model, prompt/completion/reasoning tokens, latency_ms, updated_at}`；
  `rows` 每行 `{id: "p003-00", page, index, type, level, number, original, translation}`。
- **任务系统**：`task` 表 + 租约 + 心跳 + `cursor.done_pages` 断点续跑 + `pages.json` 已有行；
  **页边界**暂停/取消；逐页 SSE `page_translated`。
- **粒度开关已取消**：`granularity` / `block_ids` / `strict_validation` / 三层缓存
  （稳定前缀缓存 / 批结果缓存 / 块级缓存）/ `translation_cache.json` 全部删除。

### 2.4 扫描件（影印 PDF）—— 第三轮新增

影印件里 `page.get_text()` 返回空串：没有 span、没有字号、没有矢量层，
行聚类 / 段落切分 / 公式恢复**整套失效**。既然内容只存在于像素里，就**正文与译文都交给模型**：

```
页图（另渲 200dpi）→ 视觉模型 → 该页 Markdown 原文（只转录、不翻译）
                       ↓ 切块（heading/para/formula/caption/table/ref）
                既有页级翻译链路 → 中文译文（该页与整页一起出原文 + 译文，下游一行都不用改）
```

- 判定：该页文本层字符 < 40 **且**含整页图像（不用 `== 0`：影印件常带零星 OCR 残渣）。
- 读页提示要求：只转录不翻译；标题一层 `#`；公式 `$$…$$`（LaTeX）；图注加粗；
  不转录页眉页脚页码；**看不清写 `[?]`，不许靠语义猜**。
- 扫描页**不跑**公式候选与插图检测（整页图会被判成一张巨型插图，且没有矢量层可审计）。
- 标题：第 1 页是扫描页时取模型识别出的**最浅层标题**（`#` 优于 `##`）。
- 离线：内置 `mock-vision`（**非默认**）——无密钥也能跑通整条链路。

## 5. 关键设计决策（当前结论）

1. **不信任 PyMuPDF 的文本块边界**：只把 span 当证据，自研「基线聚行 → 行距基线切段」。
2. **Markdown 是内容事实源，MySQL 只存定位**：避免"三处存正文 → 三处不一致"。
3. **块 ID 带论文前缀**（`turboquantic-p07-b12`）：`block.id` 是全局主键，无前缀会与第二篇冲突。
4. **一页一次调用，原文也由模型产出**：同一次调用里先忠实转录、再翻译，两份 Markdown 的块
   按序号天然对应（只在块数不同时做一次 `difflib` 序列对齐）——**不需要把整页译文切回
   `block_id`**，也**不做校验、不做回退补译**（旧版的 `page_aligner`、严格校验档、回退补译
   与三层缓存均已删除）。
5. **公式不做特殊处理，模型可信任**：整页页图与页内文本一起交给模型，它返回的 LaTeX **直接采用**；
   抽取出的 B 级公式本身可能是坏的，锁死等于忠实保留错误。
6. **Block 存裸文本，Markdown 标记由生成器统一加**：标题不带 `#`、图注不带 `**`、公式包 `$$…$$`；
   OCR 侧存带标记的文本会导致事实源叠两层（`## ## 0.2 PRIOR WORK`）。
7. **扫描件正文与译文都来自同一次页级调用**：读页阶段只转录不翻译（保住原文事实源），
   翻译阶段与整页一起出原文 + 译文；不再有"只补译错位块"这一步。
8. **分层不反向依赖**：`parsing/` 不 import `services/`；需要模型的地方用可调用钩子注入
   （`parse_hooks.build_repair_fn` / `build_vision_fn`），CLI 与任务处理器共用同一份。
9. **前缀缓存靠字节级稳定的前缀**：简报、术语表与**全文标题骨架**整篇不变且放在 prompt 最前面，
   严禁混入时间戳/页码/统计量；**前文历史必须完整且逐页追加**（第 N 页与第 N+1 页的 prompt
   从开头到"第 N-1 页结束"逐字节相同 → 前文全部命中缓存），因此它紧跟在稳定前缀之后、
   且表头不带页码。窗口 1M token 下不做滑窗截断。

## 6. 已知限制

- **未接入真实模型时**翻译走 Mock 占位（链路真实、内容占位）；`/models` 填密钥后自动切换。
- **解析公式候选质量受文本层限制**：带根号/分式的复杂公式仍会落到 B/C 级（解析质检项，设计预期）。
  **公式人工复核已下线**：阅读器展示的公式一律以 Markdown（页级产物）里的 LaTeX 为准，解析公式卡只在 `?source=parse` 时供质检参考。
- **公式回渲染校验未接入**，因此不判 A 级。
- **扫描件质量 = 视觉模型质量**：识别错的字会被翻译放大，且没有文本层可对照；
  扫描页也不产出公式卡（公式以 `$$…$$` 留在正文里，无法回渲染校验）。
- **扫描件没有 bbox**：块坐标是等分整页的虚拟横带（只为稳定阅读顺序），
  页图上叠加块框的可点选定位在扫描页不可用（页级对照仍是整页页图 + 该页行）。
- **旧版块级译文不再计入进度**：进度口径已改为**页**（`pages.json` 里有对齐行的页数），
  历史遗留的 `md/translation_cache.json`（旧三层缓存的批结果）已不被读取，重跑翻译按页重来。
- **单用户免登录**（`user_id=1`），无鉴权，仅监听本机。

## 15. 第十轮变更摘要 —— 目录建树改成"编号优先" + 翻译补上连贯记忆

> 起因：用户发现**目录顺序不对**（`1.2 INNER-PRODUCT` 排到附录 A 之后、`2 EXPERIMENTS` 被挂到 `1` 下面），
> 修好后追问"翻译时应该像对话一样把前文也发过去，为什么 markdown 还会不一致"。

### 15.1 目录顺序错乱的根因（已修）

- **两套层级都不可信**：① 页级产物里 heading 的 `level` 就是**模型写的 `#` 深度**（逐页独立调用，
  没有跨页记忆，同一层级在不同页拿到不同深度：`1 TURBOQUANT…` 是 `#`、`2 EXPERIMENTS` 却是 `##`、
  `1.2 INNER-PRODUCT…` 又是 `###`）；② 解析器的 `heading_level = min(2 + 编号点号数, 6)`
  （`1` → 2 级、`1.1` → 3 级，**整体偏一层**）——它还是 prompt 里给模型的页内文本前缀来源。
- **旧建树**：往上找第一个 `level` 更小的项当父节点 + "编号前缀对不上就抛成顶级" →
  `2 EXPERIMENTS` 挂到 `1` 下、`1.2` 被抛到顶级排在附录后。
- **新算法（编号优先）**：`_adopt_appendix_letters`（从 `B.1` 反推出父标题 `B`，没有 `X.n` 子节的
  `A NOVEL FRAMEWORK` 不会误判）→ `_apply_semantic_levels`（层级 = 编号点号数 + 1，无编号章节一律顶级）
  → `_nest_outline`（父节点 = 前面最近的、编号是本文编号**严格前缀**的标题；找不到就顶级，
  整篇无编号时才退回 `level` 栈式嵌套）。同一套规则抽成 `generator.section_depth`，全链路共用。
- **实测**：24 条标题从"乱挂乱序"变成文档顺序 + 正确嵌套（`1.1/1.2` 归 `1`、`2.1~2.4` 归 `2`、
  `B.1/B.2` 归 `B`、`C.1~C.3` 归 `C`、附录 A/D/E 顶级）；新增 `tests/test_outline.py` 5 项回归。

### 15.2 翻译补上"连贯记忆"（按用户要求改在翻译侧）

1. **全文标题骨架进稳定前缀**：`build_outline_skeleton` 把整篇的"编号 → 层级"映射（`# 1 …` / `## 1.1 …`）
   放进 prompt，**整篇字节不变** → 前缀缓存仍然命中。骨架取自解析索引，并沿用"是不是真标题"的判据
   剔掉伪代码行与表格数值行；扫描件没有文本层时退回任务开始时已有产物的标题行。
   系统提示同步改成"标题层级**必须与骨架一致**，骨架里没有的按编号深度推断，同一层级全文一致"。
2. **完整前文历史（连贯记忆 + 缓存友好）**：`history_context` 把第 1..N-1 页的**整页原文 + 译文**
   逐页附在稳定前缀**之后**。为什么不是"最近几页的尾巴"：**前缀缓存比的是最长公共前缀**，
   历史完整且逐页追加时，第 N 页与第 N+1 页的 prompt 从开头到"第 N-1 页结束"逐字节一致，
   于是整段前文都命中缓存（约 0.1× 计费）；而滑窗每页都在挪，头部一变后面全部重新计费 ——
   既丢记忆又丢缓存。两个实现细节：① **表头逐字固定、不带页码/页数/时间**（任何随页变化的字符
   都会把公共前缀截断在它那里）；② 并发调度下只取"紧邻且连续已完成"的那一串页（遇缺口就停，
   避免"第 4 页缺席但第 5 页在场"的错位拼接）。上限 `CONTEXT_MAX_CHARS = 200 万字`
   只是护栏（目标窗口 1M token），触顶时才**整页地**从最早的页丢并记 warning。
3. **修正给模型的层级参照**：`page_source_text` 原来用 `heading_level`（偏一层）拼 `#`，
   现在改用 `section_depth(编号)` —— 输入参照、骨架、目录、阅读区四处终于同一套。
4. **任务参数**：`context`（默认 true）/ `context_chars`（默认 200 万字护栏）；页产物新增
   `prev_context_chars` 便于核对。

### 15.3 实测与验收

- **真实模型复译第 7 页**（原来写成 `## 2 EXPERIMENTS` / `### 2.1 …`）：输出变成
  `# 2 EXPERIMENTS` / `## 2.1 EMPIRICAL VALIDATION`，与骨架一致；落盘行 `level = 1 / 2`（语义层级），
  `prev_context_chars = 7276`，对齐仍为 `exact`。prompt 5720 token / completion 2845。
- `pytest` 全绿（新增 `test_outline.py` 5 项、`test_page_translate.py` 7 项：

  遇缺口停止、溢出整页丢弃、前缀字节稳定）。
- **真实数据实测（完整历史与缓存）**：稳定前缀 766 字；第 10 页前文 5.6 万字、第 22 页前文

## 17. 第十一轮变更摘要 —— 跨页衔接（页尾断词 / 续句）

> 起因：用户截图指出"逐页翻译在页尾的衔接有点问题"（第 1 页尾 `communication bot-` 与第 2 页首 `tlenecks`
> 拼不上，译文出现「通信瓶-」与以「……」开头的半句）。

### 17.1 现象与根因（三层）

| 层 | 现象 | 根因 |
|---|---|---|
| 输入 | 模型只看得到当前页 | 页尾断词/断句的"另一半"在下一页，模型手上没有 → 要么硬断、要么猜 |
| 输出 | 原文忠实转录，连字符保留在页尾 | 中文没有词边界，一旦把断词拆开，读者看到的两个"词"都无法复原 |
| 产物 | 每页独立存储、独立渲染 | 页边界的"半句"在两侧各自看都合法，拼起来才发现重复/断裂 |

验证用的硬证据：`turboquant-online-vector-iclr-26` 第 1↔2 页边界
（原文 `communication bot-` | `tlenecks`；译文「通信瓶-」；下行以「……在加速器上」开头）。

### 17.2 修法（输入 → 提示 → 读取三层，全部落地）

- **输入侧**：`page_lookahead()` 取下一页开头 6 行 / ≤1200 字，带「仅上下文」标记，
  插在【本页】之后；它**不参与前缀缓存区**（属于页内变量部分）。
- **提示侧**：`SYSTEM_PROMPT` 新增【跨页衔接（三条硬规则）】：
  1. 译文**不得出现断词连字符**（`bot-` + `tlenecks` 合回 `bottlenecks`；页尾原文照录、但译文要写成完整词）；
  2. 续句必须是**完整句子**，且不得以「……」或「（承接上页）」开头；
  3. 下一页开头是**仅供衔接参考的上下文**，原文转录仍只限本页。
- **读取侧**（关键选择）：`page_continuity()` + `mark_rows_continuity()` 放在
  `reader_service.page_translations()` 里**读时执行**，对副本行打标记并清理：
  给旧产物补上 `continues` / `continued_from_prev`、去掉译文里「……」开头与行尾连字符。
  代价是一次 O(页行数) 的纯内存操作，收益是**存量产物不用重译**。
- **前端**：`ReaderRow` 新增 `pending` / `deferred`；`usePageRows.markBoundaries()` 把
  "上行 continues + 下行 continued_from_prev"的**下行译文位**改成「续下页」；
  `ReaderView` 把"存在活跃翻译任务"传给 `ReaderPageRows`，未出译文的行显示「**等待翻译**」。

### 17.3 顺手修掉一个真 bug：长论文 id 撑爆 `chunk.id`

重跑 `scripts/e2e_check.py` 时在第 9 项索引构建处炸出
`pymysql.err.DataError (1406, "Data too long for column 'id'")`：

- `chunk.id = "{paper_id}:{chunk_type}:{首块 id}[-{末块 id}]"`，最坏
  `48 + 1 + 16 + 1 + 19 + 1 + 19 = 105` 字符（`slugify` 上限 48、块 id 前缀 12）；
- 但老库该列是 `varchar(64)`，模型侧 `create_all` **不会 ALTER 已有列** → 只有短 id 的小论文跑通过，
  真实论文名一长就整批插入失败（此前只在 `_smoke` 上跑过索引，所以没暴露）。

修法（两处，都不动业务逻辑）：

- `models.py`：`Chunk.id` / `Block.chunk_id` 改 `String(128)`；
- `session.py` 新增幂等的 `repair_column_widths()`（查 `information_schema` 里比要求窄的列才 `ALTER`），
  由 `init_db()` 调用 → **服务启动即自动修补**，`init_db()` 返回值新增 `repaired` 字段便于核对。
  实测日志：`已加宽历史窄列：chunk.id: varchar(64) -> varchar(128)；block.chunk_id: varchar(64) -> varchar(128)`。
- 防回归：新增 `tests/test_schema_widths.py`，用最坏情况反推长度并断言列宽够用。

## 18. 第十二轮变更摘要 —— 左侧「原 PDF」改成真 PDF（可复制文字）

> 起因：用户指出"当 pdf 不是扫描件时，前端左侧应为真实 pdf（可以复制文字）而不是图片"。
> 确认过的口径：**逐页贴合**保留现有布局（A 方案）、**扫描页继续用位图**、
> **PDF 划词不锚定块**（只保留选中文字，可解释/复制）。

### 18.1 之前是怎么错的

左栏那两处（"纯原 PDF" 单栏 / "对照 + 原 PDF"）挂的是
`<img src="/api/v1/papers/{id}/pages/{n}">` —— 后端 150dpi 渲染的 **PNG 位图**：

- **选不中、搜不到、复制不了**：读者想引一句原文只能手打，Ctrl+F 也搜不到；
- 缩放发虚（位图重采样），而矢量 PDF 放大永远清楚；
- 对电子版论文来说，这份位图反而是**冗余存储**（PDF 里本来就有矢量+文字）。

### 18.2 现在的做法

- **后端**：`GET /papers/{id}/file` 加 `content_disposition_type="inline"`
  （带 `filename` 的 `FileResponse` 默认发 `attachment` → 浏览器会下载而不是就地把 PDF 打开）。
- **前端**：新增 `frontend/src/components/reader/PdfPage.vue`（**pdfjs-dist**）
  - 按页渲染：`canvas`（矢量，按 `width × dpr` 出图）+ 文字层（`TextLayer`，真文字可选中/复制）；
  - **同一篇只加载一次 PDF**（模块级 Promise 缓存），22 页共用一份 document；
  - **进入视口附近才渲染**（`IntersectionObserver`，`rootMargin: 900px`）——
    实测滚筒屏时 22 个 canvas 里只有 2 个真出图，其余保持 300×150 占位；
  - 渲染前用 `PageInfo.width/height`（PDF 点）撑 `aspect-ratio`，不会"先扁后弹"；
  - 宽度变化（页宽滑杆/窗口缩放）→ 重渲；渲染失败 → 自动回退后端的位图页图。
- **分流规则**：`PageInfo.has_text_layer`（解析时就算好了）为 `true` 走 pdf.js，
  扫描页（`false`）继续用位图 —— 扫描件的 PDF 里就是一整页图，走 pdf.js 白搭内存；
  未解析/拿不到页信息的论文也回退位图。
- **划词**：`onMouseUp` 新增一条分支 —— 选区落在 `[data-pdf-page]` 里时进
  `anchored: false` 状态：浮层只留「**AI 解释 / 复制**」（高亮与笔记靠 `block_id + 字符偏移` 定位，
  PDF 文字无法映射回去），解释弹窗也不再提供"存为批注"，并带上
  "来自原 PDF 划词（无段落上下文与锚点）"的说明。
  后端 `explain_selection` 对 `block_id` 本来就是可选的，因此**后端零改动**就支持无锚点解释。

### 18.3 验收（全部实测）

| 项 | 结果 |

### 18.5 用户复看后的三处返工（已实测修复）

| 反馈 | 根因 | 修法 |
|---|---|---|
| 划词浮层在文字靠右时排版乱（按钮变竖排"AI 解/释"） | 定位用 `x = min(视口宽 - 320, 选区左)` 硬夹：**菜单实际宽度**（带 5 个色块时 ~330px）超过留下的空间，flex 子项默认会**收缩** → 文字换行；且常量一旦猜小，菜单还会溢到屏外 | 菜单改为**量完再拉回**：先按原位渲染 → `offsetWidth` 量宽 → `shift` 把溢出量除去；CSS 加 `flex: 0 0 auto` + `white-space: nowrap` + `flex-wrap: nowrap`（永不再换行）。实测：选区右边缘 928px 时菜单从 928 自动左移到 811，单行、完整可见 |
| 逐页贴合时左栏顶部白空太多 | `.pg-pair .col-image .media-box { position: sticky; top: 34px }`（最早是给工具栏留位）——但 **sticky 的参照物是滚动容器**，而滚动容器上边已经在工具栏下沿了，这 34px 是纯白空 | `top: 34px` → `top: 2px`。实测：页图顶边与滚动容器上边间距 **34px → 2px** |
| 渲染偏右 + 不太清晰 | ① 首次进入视口时容器**还没排版**（`clientWidth = 0`），代码退回"期望宽度"出图 → 画布比外框宽 122px，被 `overflow:hidden` 裁掉（看起来就是"页面偏右、右边被切"）；② 位图按猜的宽度出，与实际显示宽度不 1:1 | 把"量得到的容器宽度"作为**唯一**渲染宽度来源（量不到就等 `ResizeObserver`），位图 = 显示宽度 × `dpr≤2`；外框变宽变窄自动重出（带重出预算，避免"内容宽反过来影响外框宽"的弹窗反馈回路） |

> 连带修掉一个更隐蔽的坑：**首次进入视口一律不渲染**。原来用 `requestAnimationFrame` 重试量宽，
> 而 
> 后台/未聚焦标签页的 rAF 会被节流到几乎不跑 → 页面停在那里永不渲染。现在完全依赖
> `ResizeObserver`（`observe()` 后规范保证会给一次初始尺寸回调），不依赖帧调度。

### 18.7 用户复看第二轮：文字层字号、侧栏卡顿、要不要改原生渲染

**① "选中文字与实际文字不对应"（真 bug，已修）**

根因：之前手写的"最小文字层 CSS"只写了"透明文字 + 绝对定位"，**没写 `font-size`** ——
隐形文字于是用继承的 13px，而画布上的字形是 `--total-scale-factor × --font-height` px，
两者不一样大、位置也对不上，选中的框自然套不准。

关键换算（从 pdf.mjs 源码确认 + 实测）：`--font-height` 是**页面单位**
（ICLR 正文实测 9.96 ≈ 10pt，不随视口缩放；缩放在 `--total-scale-factor` 里），
所以官方公式 `font-size = --total-scale-factor × --min-font-size × --font-height`
配合 span 上的 `scale(1/--min-font-size)` 正好抵消。现按官方 `pdf_viewer.css` 的 `.textLayer` 段照改。

验证（在画布像素里测墨迹包围盒）：每行文字层的框与字形墨迹覆盖率 **0.97–0.99**（左/上偏差 1–2px）；
选中 `mirrokni@google.com` 的截图 `data/logs/shot/sel-align.png` 显示高亮带严丝合缝套住文字。

**② "开关侧栏容易卡住"（真 bug，已修）**

根因有两个叠加：

- `visible` 是个**粘性标志**（"曾经进入过视口"），滚过全篇后 **22 页都算可见**；
- 侧栏开合会让每页的 `props.width` 变 → 每页都立即**重新光栅化 + 重建文字层**。

于是"滚一会儿再开侧栏"＝一次重画二十多页，必卡。修法：**出图与显示解耦**

| 手段 | 做法 |
|---|---|
| 缩放不再重出 | 页面内容放在固定尺寸的 `.pdf-surface` 里，外层只改 `transform: scale(k)`（画布与文字层同步缩放，对齐不跑） |
| 重出要先复核位置 | 重出前用 **实时几何**（`nearViewport()`）判一次，不再只看粘性标志 |
| 重出要值得 | 倍率偏离 >15% 才值得，且防抖 450ms；离屏页不重出 |
| 可观测 | 每次出图给宿主加 `data-renders` 计数，方便自检/排查 |

实测：开合侧栏 5 次 → **额外重出 0 次**（旧逻辑会重画已渲染的全部页）；点击到界面更新的耗时 14–70ms。

**③ "能不能浏览器原生渲染"（结论：能，但不建议当主路径）**

| 方案 | 代价 |
|---|---|
| 每页一个 `<iframe>` 套浏览器原生阅读器 | **每页一个 PDF 插件实例**（就算 lazy，滚过全篇就是 22 份），内存与启动开销远大于共用一份 document |
| 单实例 `<iframe>` 整篇（靠 `#page=N` 跳转） | 与现有"**每页贴在该页译文旁**"的对照布局冲突；换页要重设 src，有闪烁；样式/联动不可控 |
| 保留 pdf.js（现状） | 已解决卡顿与选中对齐；文字层可选中/复制/Ctrl+F，页宽缩放不发虚 |
| 想要原生体验 | 工具栏「**打开原 PDF**」直接新标签页开原生阅读器（`Content-Disposition: inline` 已支持） |

所以主路径继续用 pdf.js；需要"完全原生"时走那个按钮。

**顺带记下两个只在特定环境暴露的坑**（已加兕底）：

- **隐藏标签页里 IO / RO / rAF 全都不回调**（实测 `visibilityState=hidden`）：
  PDF 会永远停在"正在渲染…"；现在用定时器 + `visibilitychange` 兕底启动，
  并在隐藏期间把 `requestAnimationFrame` 临时换成 `setTimeout`（pdf.js 的分片渲染靠 rAF 推进，否则画一半就挂住）。
- 滚动条出现/消失会引起容器宽微变 → 反复重出；`.reader-content` 加 `scrollbar-gutter: stable` 消除这个抖动源。

验收：`scripts/frontend_check.py` **41/41**、`pytest` **102 passed / 1 skipped**、`scripts/e2e_check.py` **35/35**。

## 19. 第十三轮变更摘要 —— 任务幂等 / 工具栏减噪 / 划词不跨栏 / 页边句子

> 用户连续提的四条：① 避免重复运行翻译任务；② 运行中主按钮还写着「继续翻译」；
> ③ 「实时」「简报」文字冗余；④ 页间翻译把一句话拆成了两句；外加 ⑤ 右栏划词会拖进左栏 PDF。

### 19.1 「重复运行翻译任务」的真根因：时钟口径不一致（真 bug，已修）

`translation_service._task_is_live()` 用 `datetime.now()`（**本地**）去减 `utils.now()` 写的
**UTC** 时间戳 —— 本地是 UTC+8，于是**刚建好的任务被算成"8 小时前的僵尸"**：

```
第 1 次 POST → 建 t-A（pending）
第 2 次 POST → 找到 t-A → 判定"不活" → _drop_task(t-A) 取消 → 又建 t-B
```

而 t-A 可能已经/正在被 worker 执行 → **同一篇两套翻译并发**，产物互相覆盖。
实测三次连点建出了三个任务（`t-4741…/t-e797…/t-60ef…`）。

修法：`_task_is_live` 改用 `utils.now()`（UTC）。顺手把 `force`（重译）也纳入复用：
**一个任务在跑时不再新建**（想真重来就先停止）。返回值加 `reused` 字段。

### 19.2 前端三处减噪与防重复

| 项 | 做法 |
|---|---|
| 运行中主按钮 | 显示「**翻译中…**」并 `disabled`（`:disabled="!!activeTask \|\| busyTranslating"`），旁边保留「停止」 |
| 防连点 | `busyTranslating` 在途锁 + `activeTask` 存在时直接提示「已有翻译任务在跑（N/M），先停止或等它结束」 |
| 「实时」徽章 | **去掉**（SSE 是否连着是实现细节）；只有降级「轮询」/「连接中」才提示 |
| 「简报」勾选框 | **去掉**（有就用、没有就自动生成；`brief=false` 仍保留在 API 上给脚本用，左栏「术语」页签可编辑简报） |
| 论文库「继续翻译」 | 同样识别 `reused`，提示"已有任务在跑，已沿用该任务"，不再假装新建 |

实测：点一次 → 按钮变「翻译中…」且禁用、「停止」出现；再连点两次 → 活动任务数仍为 **1**。

### 19.3 顺带修的进度分母

`start_translation` 算 `total_items` 时**忽略了 `pages`**，于是"重跑第 1、2 页"的任务在任务页显示 `0/0`。
现在指定页时分母 = 指定页数。

### 19.4 划词不跨栏（用户报：右栏选字会拖到左边 PDF）

两侧是并排的独立内容，从右栏往左拖会继续吞进 PDF 那串**隐形文字**（选中的东西和看到的不一样）。

第一版写法（夹取 `getRangeAt(0)` 的 end）**是错的**：拖拽向左产生的是**反向选区**，
`range` 的 start/end 与 `selection` 的 anchor/focus 不是一回事，直接 `setEnd` 会把选区**翻到 PDF 那侧**（实测 3590 字的整页选中）。
现在改为：记住**最后一次两侧同栏**的选区，一旦 anchor/focus 分属两栏就回退到它（没有则折叠到锚点）。

实测：右栏起手拖进 PDF → 选区仍停在右栏（`Amir Zandieh`，12 字）；PDF 起手拖进右栏 → 停留在 PDF ✓。

### 19.5 页边句子：从"补成完整句"改成"该停就停、该接就接"

第 11 轮那条硬规则是"**续句必须是完整句子**"——它与"只看得到本页正文"的契约互相打架：
模型只能把半句**圆成一个完整句**，下页再把剩下的半句当新句译 → 一句被拆成两句（用户截图里的
「…主要归因于通信瓶颈。」+「加速器上 HBM 与 SRAM 之间…」）。

新契约（提示 + 解析器事实双管）：

1. **prompt 注入【页边界事实】**：`render_edge_facts(page_continuity(...))` 告诉模型
   「本页开头：承接上一页 / 新起句子」「本页末尾：句子延续到下一页 / 已结束」——
   这件事在页图上并不显眼（常常只是没写句号），直接给事实比让它猜可靠。
2. **规则改写**：页尾是半句就**停在句中断处**（不补句号、不补下半句、不用「……」占位）；
   页首承接就**接着上一页译文的最后几个字**往下写（不重复、不用「即/也就是说」这类重新起句的引导词，
   需要时可川「——」把补充成分接上，并把上页缺的中心词补全）。
3. **前端不再藏内容**：以前把页尾半句的译文整格换成「续下页」（那是为了遮"半截词 + 整句重译"的重复）；
   现在半句本身是**正确内容**，改成行尾/行首的小徽章提示（「承上页」「续下页」），文字照常显示。
4. **读时清理收窄**：`_LEAD_JUNK` 不再剥「——」（实测「…通信瓶颈——它出现在加速器上…」是最顺的读法），
   只剥「……」/「（承接上页）」这类似占位噪声。

真实模型实测（force 重译第 1–2 页，两次调用）：

| | 文本 |
|---|---|
| 第 1 页末行译文 | `…为其提供服务需要大量内存并会增加推理延迟。这种延迟主要归因于通信瓶颈`（**无句号，停在句中**） |

### 19.7 PDF 拖拽划词：整页闪烁 / 往下覆盖 / 跨页复制（都由文字层自己接管）

**先说实测到的三个事实**（真实鼠标拖拽 + 逐事件记录 `selectionchange` 的 `anchor/focus`）：

1. 文字层的 span 是**绝对定位**的，层自己没有行盒 → 点在**行间、词间的空白**上时，
   `caretRangeFromPoint` 交回的是**层容器本身**（`focusNode = .pdf-text-layer`，offset = 第几个子节点）：
   offset 递增时选区从锤点一路铺到层末（实测 131 字 → 3176 字，矩形从 -212 铺到 766，即整页）；
   offset 落在 0 时反过来倒长到页首。**往下拖过一行行的间隙会反复触发它**。
2. 这个错误状态**会被画出来一帧**（`selectionchange` 交到手上时本帧已经画过了）——
   所以"事后把焦点拉回来"必然看到"瞬间整页全选"的闪烁（用户报的就是它）。
3. Chrome 的 `Selection` 实际**只保留一段** range（`addRange` 第二段会被合并成一段，实测
   `rangeCount === 1`）；而本阅读器是"每页 PDF 一栏、旁边紧跟该页译文"，
   于是跨页选 PDF 时中间那些**译文会被一起圈进选区**（复制出来就混着非 PDF 内容）。

**最终做法：按下落在 PDF 文字上就接管这次拖拽**（`PdfPage.vue` 顶部模块级的共享状态，
22 个页面实例必须共用一份，否则跨页两端凑不到一起）：

| 环节 | 做法 |
|---|---|
| 挡掉原生划词 | `selectstart` 里 `preventDefault`；**从 mousedown 就挡**（事后再修必闪一帧）。双击/三击 `detail ≥ 2` 放行，选词/选行保持原生 |
| 焦点自己算 | `caretRangeFromPoint`，**只接受"某个 PDF 文字层里的文本节点"**；点不到就上下探 2/4/7/11/16/22px 找最近一行（行间空白也能选中）；真探不到（空句、插图区）**停在最后一次有效位置**，不膨胀 |
| 跨页 | 焦点落在另一页的文字上也照收 → 一段 range 跨两页 ✓ |
| 不让译文进选区 | 拖拽期间给 `<html>` 加 `pm-pdf-drag`，CSS 让 `.col-rows/.pg-rows/.pg-head` 等**非 PDF 内容 `user-select:none`** —— Chrome 会把不可选内容从选区里跳过（实测 `toString()` 4984 → 3631 字，正好等于 PDF 部分）。★ **松手后不能立刻摘这个类**：同一段 range 还在，摘掉译文立刻又被算回来（实测 2106 → 3400 字）；改为"选区只要还盖在 PDF 上就保持" |
| 长距离跨页 | 拖到滚动容器上下 48px 内自己 rAF 滚动（原生划词被挡掉后浏览器不会代劳） |

### 19.10 页边界「同一个词出现两次」的真根因与修法

用户截图：第 1 页末行译到「…这种延迟主要归因于通信**瓶颈**」，第 2 页首行又写「…之间的**瓶颈**」——
同一句话被两页各写了一遍中心词。用户的猜测是"模型没拿到下一页信息"，**实测数据否定了这个猜测**：

| 页 | 存下来的证据 | 说明 |
|---|---|---|
| page 1 | `lookahead_chars = 1418` | **拿到了**下一页开头（就是 `tlenecks between HBM and SRAM…`）✓ |
| page 1 | `edges = {ends_mid: True}` | 也拿到了"本页末尾延续到下一页" ✓ |
| page 2 | `prev_context_chars = 0` | **没拿到**上一页译文 ✗（全量重译时各页并发，前文还没落盘） |
| 两页原文 | `…attributed to communication bot-` / `tlenecks between …` | **同一个词被页边界劈成两半** |

**真根因**：这是"折行词"的两侧**都**在补全 —— 上一页为避免留下「通信瓶-」必须补成「通信瓶颈」，
而下一页自己的原文开头就是 `tlenecks`（且后文还有 `bottlenecks`），于是它也写了一次中心词。
即使 page 2 拿到前文，契约里"把中心词补全"这条也会引导它重复。

**修法（单边责任）**：契约改成"**本页补全、下一页不许再写一遍**"，并且**不依赖能否看到上一页译文**（按原文就能判断）：

```
4. 页边界被折断的词：本页补全，下一页不许再写一遍。
   - 页尾 `communication bot-` 这种折行：本页补成完整词（→「…主要归因于通信瓶颈」），不许留「通信瓶-」；
   - 下一页开头遇到同一个词的后半截（原文形如 `tlenecks between HBM and SRAM on accelerators, …`）：
     **不要**再把那个词写一遍，直接从它**后面的成分**接着译（→「HBM 与加速器上的 SRAM 之间、或跨分布式集群之间。」）。
```

**真实模型验证**（按顺序重译第 1、2 页，让第 2 页带上前文 `prev_context_chars = 5020`）：

| | 文本 |
|---|---|
| page 1 末行 | `…为其提供服务需要大量的内存需求并带来更高的推理延迟。这种延迟主要归因于通信瓶颈` |
| page 2 首行 | `HBM 与加速器上的 SRAM 之间、或跨分布式集群之间。通过压缩或量化模型权重与激活值…` |
| 连读 | `…主要归因于通信瓶颈 HBM 与加速器上的 SRAM 之间、或跨分布式集群之间。` ✓ 中心词只出现一次 |

**遗留提示**：`mode=retranslate`（前端"重新翻译"）时各页是**并发**跑的，前一两页可能还没有彼此的前文
（page 2 那次就是 `prev_context_chars = 0`）。新契约不依赖前文所以不会再重复；但要靠"前文"统一术语/句式时，
按页顺序单独重跑（或在低并发下跑）更稳。

### 19.11 第二十一轮 —— 整句归上一页 / 取消并发（并验证前缀缓存）/ 解析与翻译合成一个入口

**1）跨页那句整句收在上一页。** 上一版契约是"页尾停在句中断处、下一页接着写"，读起来页尾总是半句。
现在改成：**页尾用【下一页开头】把这句在本页译完**（一直译到真正的句末），
**下一页跳过这半句**、从下一个句子开始 —— 一句话只出现一次，页尾也是完整句。

| 页 | 原文 | 译文 |
|---|---|---|
| page 1 末 | `…attributed to communication bot-` | `…这种延迟主要归因于通信瓶颈，它出现在加速器上的 HBM 与 SRAM 之间，或跨分布式集群。` |
| page 2 首 | `tlenecks between HBM and SRAM …, or across distributed clusters.` | `通过压缩或量化模型权重与激活值，…`（**跳过**已被上一页译完的半句） |

【页边界参考】的措辞同步改成"页首那半句已由上一页译完，本页跳过它""页尾请用【下一页开头】把这句译成完整句"
（`render_edge_facts()` + `tests/test_page_translate.py` 同步）。

**2）取消并发：逐页翻译改成严格串行，并验证前缀缓存真的在吃。**

- 新增配置 `translate_sequential: bool = True`（默认开）→ 调度器的 initial/maximum 都压成 1，仍保留
  `AdaptiveScheduler` 的重试/退避能力。理由：并发时第 N 页可能在"第 N-1 页还没落盘"时构建 prompt
  （实测 `prev_context_chars = 0`），既丢连贯性，又让每页 prompt 的历史尾巴形状不一致 → 前缀缓存被打碎。
- **把缓存命中量接出来**：`PageCallResult` 新增 `cache_hit_tokens` / `cache_miss_tokens`
  （取自 provider 已解析的 `usage.prompt_cache_hit_tokens`），写进每页产物、任务汇总，并逐页打日志
  `第 N 页：prompt X token（缓存命中 A / 未命中 B）`。

实测（真实模型，一次任务翻第 5、6 页）：

| | prompt | 缓存命中 | 未命中 | prev_ctx |
|---|---|---|---|---|
| page 5 | 13170 | **8448（64%）** | 4722 | 25837 字符 |
| page 6 | 15869 | **10880（69%）** | 4989 | 32960 字符（比上页多出 page 5） |
| 任务合计 | 29039 | **19328（67%）** | 9711 | `concurrency_peak = 1` ✓ |

命中 + 未命中正好等于 prompt，说明统计口径正确、**缓存机制有效**；page 5 那 64% 里有一部分是被
"刚改了 system prompt"打掉的历史（下一次同前缀请求才会全命中）。

**3）"解析 PDF"与"重新翻译"合成一个入口（选项 B）**，并且状态前后端对齐：

- **卡片上只留「翻译」一个入口**，文案随状态变：未解析 →「翻译」；翻译中 →「继续翻译」；全译完 →「重新翻译」。
  **未解析时点「翻译」不需要用户先点解析**：后端 `/papers/{id}/translate` 发现没有页图，
  就替用户建一个带 `then_translate` 的 PARSE 任务，解析完成后由 `handlers._chain_translate()` 自动开翻译任务。
- 「解析」不再与「翻译」并列暴露：⋯ 菜单里只留 **「重新解析」**（强制重来，不附带翻译），
  原来的「解析 PDF」「重新翻译」两个菜单项都去掉了。
- **不会自动翻译**：导入时的 `auto_parse` 仍然只解析；翻译必须在**用户点了「翻译」**之后才开始
  （阅读器空状态的按钮改成「解析并翻译」，也是一次点击才串起来）。
- **状态对齐**（避免"看的一头雾水"）：
  - `paper_service._to_dict()` 增加 `_align_with_disk()`：以**磁盘**为准修正 `page_count` / `translate_*` / `status`
    —— 手动删掉 `data/papers/<id>/` 后 MySQL 里的统计是陈旧的，卡片会显示「继续翻译 + 11/22」这种假状态；
    现在会如实地回到「已导入 + 翻译」。（只改返回值，不写库。）
  - 论文库新增**任务轮询**：只要还有 PARSE / TRANSLATE_MD 任务在 `pending`/`processing`，每 4s 自动 `refresh()`；
    没有任务在跑立即停 —— 徽章、进度、按钮文案都跟着后端走，不需要用户手动点「重新加载」。

浏览器实测（论文库）：未解析卡片 = 徽章「已导入」+ 按钮「**翻译**」；已译完卡片 = 按钮「**重新翻译**」；
两卡片的 ⋯ 菜单 = 重新解析 / 建立索引 / 纳入知识库 / 编辑元数据 / 删除 / 彻底删除（**没有**重复的解析/翻译项）。

### 19.12 第二十二轮 —— 进度按页实时显示 + 卡片「暂停翻译 / 继续翻译」

用户反馈两件事：翻译已经跑掉一半，卡片还停在 `0 / 480`；卡片上也没有暂停入口。

**1）分母错了：480 个块 ≠ 22 页。**
`handlers._sync_to_mysql()` 原来写 `translate_total = len(result.blocks)`（PARSE 的**块数**），
所以一篇 22 页的论文显示成 `0 / 480`。改成按**页**：`translate_total = len(result.pages)`、
`translate_done = 0`，之后的推进交给逐页回写。

**2）只在任务结束时回写 → 中途必然是旧数字。**
新增 `paper_service.set_translate_progress(paper_id, done=…, total=…)`（只 UPDATE 两列，不读磁盘），
在 `translation_service.emit()` 里**每译完一页**调用一次 —— 卡片进度条因此是**实时**的。

**3）"正在跑的任务"才是真相来源。**
- 重新翻译时磁盘上还是**上一轮**的产物，`_align_with_disk()` 会把卡片改回「已翻译 22/22」，
  而任务其实刚开始 —— 正是反复出现的"前后端状态对不上"。现在新增
  `paper_service._papers_being_translated()`（查 `TRANSLATE_MD` 的 pending/processing/paused，结果缓存 3s），
  论文**有任务在跑时跳过翻译相关修正**（`page_count` 之类的解析类修正照旧）。
- 论文库轮询把任务信息带进卡片：`paperTasks` 存 `{id,status,done,total,message}`；
  徽章 →「翻译中 / 已暂停」；进度条 → 优先用论文行（后端逐页回写，最接近磁盘事实），
  行里还是上一轮的「已完成」时退回任务计数器；「逐页翻译已完成」那行在有任务时不再显示；
  进度块 `title` 用后端 message（「已请求暂停，等待当前块结束…」这类）。
- 同一篇论文的历史任务**只认最新一个**：`/tasks` 是 `created_at` 倒序，之前的写法会让旧任务把当前状态盖掉，
  卡片会莫名出现「继续翻译」。

**4）卡片上的「暂停翻译」。**
按钮文案：有任务在跑 →「暂停翻译」；已暂停 →「继续翻译」；否则按流水线位置
（未解析 →「翻译」/ 翻译中 →「继续翻译」/ 译完 →「重新翻译」）。点击走
`POST /tasks/{id}/pause|resume` 并 toast「已请求暂停：当前这一页译完就停下」。
后端在**页与页之间**检查 `pause_requested`，所以是"停在这一页之后"，不是硬中断 ——
对用户意味着"不浪费这一次调用的钱"。

浏览器实测（scanned-demo，2 页）：点「重新翻译」→ 4s 后卡片 =「翻译中 | 0 / 2 | 暂停翻译」
（此时论文行还是上一轮的 `translated 2/2`，所以进度数字退回任务计数器）→ 点暂停 → toast + 按钮 title
变「已请求暂停，等待当前块结束…」→ 当页译完任务转 `paused 2/2`，卡片 =「已暂停 | 2 / 2 | 继续翻译」
→ 点「继续翻译」→ 任务 `pending` → `completed`，卡片回到「已翻译」；论文行 `translating 1/2` 与任务/卡片同步推进。

顺带记下一个**测试环境坑**：这个共享浏览器页在窗口没聚焦时 `page.mouse.click()` 是**静默无效**的
（连 `pointerdown` 都到不了 document）。必须先 `page.bringToFront()`；即便如此仍偶尔丢事件，
验证 UI 点击时可以直接对元素 `el.click()`（走的是同一个 Vue 事件处理器）。

### 19.13 第二十三轮 —— 极端版面的跨页衔接（图区挡在页首）+ 让模型申报 `carry_md`

用户报了两个问题：① 极端情况下的两页之间翻译；② 缓存命中比例是否正常。

**根因（都有实测证据）**
1. `page_lookahead()` 只取"下页前 6 个非空行"。碰到**图区顶在页首**的版面（p21 开头是
   `(a) TURBOQUANT$_{\text{prod}}$` / `$$ \times 10 $$` 刻度 / `![](...png)` 图片占位），
   真正的续句 `input embedding vectors during both quantization and dequantization stages.`
   在图区**后面**，根本没进 prompt → 模型只能写「…将随机旋转矩阵施加于……」（用户截图那一行）。
2. 边界判定 `page_continuity()` 按"块"判也一样漏：`head_blocks[0]` 是子图标签，
   于是提示词反过来告诉模型"本页句子已结束"，与实际相反。
3. **"让下一页自己跳过那半句"不可靠**：实测 p06 照旧把整句又译了一遍 → 相邻两页中文重复
   （局部重译时更容易发生）。

**修法**
1. `_leading_lines()` 跳过**图区噪声**（图片占位 / 坐标轴刻度 / 子图标签），并且一直取到**句子收尾**
   （`_ends_sentence`，默认 14 行 / 2200 字符，没收句再放宽 8 行）。
2. `page_continuity()` 增加**正文回退**：对面页开头第一行**小写起头的正文**才算续句；
   且与 lookahead 用**同一个窗口** —— 判定和提示词永远一致（不会出现"让模型用【下一页开头】补完、
   可窗口里没有那半句"）。
3. **`carry_md` 契约**（用户提的思路，落地版）：模型必须在 JSON 里申报它从【下一页开头】**借用的那段原文**
   （逐字符照抄，没借就空串）；下一页调用时把这段**从正文里删掉**（`drop_declared_fragment`，
   空白不敏感；找不到 / 位置太后就原样返回 —— 宁重勿丢）。这样重复从**结构上**不可能发生，
   行对齐也不会因为"少译一句"整体错位。

**代码**：`DashScopeMultimodalEmbedding` + `DashScopeReranker`（`backend/providers/embedding/providers.py`）、
工厂两条新路由、预设 `dashscope_rag`（`create_preset` 补上 reranker 类型）、
LanceDB **维度变化丢表重建**、前端 `ModelsView` 预设徽标补 reranker。
密钥落在 `data/secrets/dashscope.key`（不进版本库）。

**验证**：`tests/test_rag_providers.py` **13 项通过**、全量离线 **141 项通过**；
真实调用：12 条中文段落 2560 维、嵌入 1.05s、重排 0.32s；跨模态中文问句 → 公式裁图 0.749 / 插图 0.767；
`GET /models/presets` 可见新预设。**用户库的默认模型没动**（仍是 mock-embedding + heuristic-overlap）。

### 19.22 第三十二轮 —— RAG 语料改「双语两行」（同一 chunk：中文 + 原文）

用户选定口径：**双语各一行**。原 `build_chunks_for_paper` 只入库英文原文（解析产物），
中文提问全靠模型跨语能力；库里中文译文本来就现成（页级产物 22/22 页），这一轮把它接上。

**关键难点是"译文行 ↔ 解析块"的对齐**，迭代了三版（都用真实论文量过）：

| 版本 | 做法 | 正文 zh 覆盖率 |
|---|---|---|
| v1 | 压空白后精确签名 | 52% / 72% |
| v2 | 签名只留「小写字母+数字+汉字」（两次转写差异消失） | 55% / 80% |
| v3 | **页内字符级对齐**（difflib）+ 重叠门槛 | **100% / 98%** |

v3 又暴露"块比行细 → 整行译文被端走"（21/56 个中文 chunk 比英文侧大 2 倍以上、6 条完全重复），
改成**按行内字符占比切片并吸附句号**后：重复 0、token 比中位 1.47 → 1.23。

**落地**：chunk id 加 `:zh`/`:en` 后缀、`lang` 进 `metadata_json`（**不动表结构**）；
LanceDB 加 `lang` 列 + 语言过滤 + `all_rows()`（供下一轮词法检索）+ 表结构不符自动重建；
`/knowledge/chunks?lang=`、`/knowledge/overview.chunks_by_lang`、论文库页双语徽标。

**验证**：`tests/test_rag_chunks.py` 14 项、全量离线 **156 项通过**；真实论文探针（只读）
TurboQuant 258 行（100% 覆盖）/ AIAYN 137 行（98%）、重复 0；临时目录 LanceDB 往返 OK。

**边界**：zh 侧是按比例近似切分，**不能用于逐字引用校验**（引用校验走 en 侧，留给 /rag/query 轮）。

### 19.23 第三十三轮 —— 检索内核 + `POST /rag/similar`（跨文献技术相似度）

`backend/services/knowledge/retrieval.py`：向量召回（qwen3-vl-embedding，查询侧带 instruct）
→ 词法 BM25（整表内存打分，中文按"词+字"分词）→ RRF 融合（k=60，按 `pair_id` 聚合双语行）
→ 重排降级链（qwen3-vl-rerank 优先，失败/未配置降级词法启发式并**标明降级**）。

**接口**：`POST /rag/similar`，`scope = all | cross | paper`，支持 `query` 或 `chunk_id`（以库里
某段为查询，自动排除自身，默认 `cross` = 排除来源论文）。返回带 `scores{vector,lexical,rrf,rerank}`、
`ranks`、`paper_title`、`snippet` 与 `retrieval.notes`。

**修掉三个实测暴露的问题**：① 双语 zh/en 两行占 top-k 两个位置 → RRF 按 pair 聚合、展示名次最好的
那行；② 旧索引没有 `lang` 列导致 `select` 报错被吞 → **词法检索静默失效**（lexical_hits 恒为 0）→
按 schema 取列交集、旧表默认 en、语言过滤给出 notes；③ jieba 把"向量量化"切成一个词 → 补单字。

**验证**：`tests/test_rag_retrieval.py` 18 项、全量离线 **176 项通过**；真实链路（临时库 + 真模型
395 行 2560 维）四类查询排序合理；用户真实环境（旧索引 + mock/heuristic）`implemented=true`、
lexical_hits 从 0 → 20、降级有标注；无头 Edge 截图确认新卡片渲染正常。

### 19.24 第三十四轮 —— RAG 问答 `POST /rag/query` 打通（阶段 14–17 收口）

`rag_service.py`：ContextBuilder（编号来源 `[S1]`、**原文+译文都给**、7000 字 / 8 条预算、截断记账）

### 19.26 第三十六轮 —— 知识库页三处返工（对账 / 合并说法 / 移除与删任务）

用户口径：① 索引状态「不一致」+ embedding 模型徽标显示成 id（截图）；② 「建索引」与「纳入」合并；
③ 要能「从知识库移除」与删除任务记录。

**根因（① 的两个现象是同一件事）**：`scanned-demo` 的 10 条旧 chunk 元数据留在 MySQL，
而向量表在换模型时被整体重建 → 405 ≠ 395，且这 10 条带着陈旧的 `mock-embedding` 模型 id。
修法是**真对账**：`reconcile()` 报 `orphans/missing` 并可 `fix` 清理；`index_status` 直接给
`consistent/orphan_chunks`；`overview.embedding_models` 换成"可读名字 + 维度"。
② `index_paper` 顺带置 `in_knowledge_base=True`（建索引即纳入），界面不再有单独的纳入开关。
③ 新增 `remove_from_kb`（清向量+元数据+标记）、`POST /knowledge/remove`、`DELETE /tasks/{id}`、
`POST /tasks/cleanup`，前端对应按钮与二次确认。

**⚠️ 本轮出过一次真实事故**：新写的 e2e 测试裸调 `cleanup_finished()`（默认全库清理），
把用户 `task` 表的全部已结束记录删掉了（含 `stats_json` 的 token/耗时实验数据，不可恢复）。
论文、译文、chunk/向量、高亮、笔记、文档里的汇总数据均未受影响。
加固：`cleanup_finished(statuses, paper_id)` 加 `paper_id` 安全阀并在 docstring 写明"测试必须传"、
非法状态返回 0 不再回落全清、测试改传 `paper_id`。

**验证**：`tests/test_kb_lifecycle.py` e2e 9 项通过、全量离线 **196 项通过**；真实库对账

任务删除 404 / 非法状态 0 条保护均生效。
