## 0. 一句话

把"翻译"从一个**单路、只产出双语对照**的产物，改造成一条**两路流水线**：两个模型**并发**处理同一篇论文，
各自按自己的语义边界分块；翻译/转录完成后再**注入新的理解提示词**，两路做**不同的**理解任务；
`chunk` 既是检索单位，也是理解结果的**引用基准单位**；前端把阅读、理解、知识库、学习收成四个面。

```
PDF → 解析 → 两路并发（A 转录 / B 翻译）→ 两路各自分块 → 两路各自理解 → 前端统一展示
```

## 1. 系统图（需求⑫）

```
                        ┌──────────────── PDF ────────────────┐
                        │ 解析：IR + blocks.json + 150dpi 页图  │
                        │ 解析器块 id 稳定：turboquanton-p01-b01 │
                        └──────────────────┬──────────────────┘
                                           │  ↑ 这一份块索引两路都能拿到 = 共享坐标格
              ┌────────────────────────────┴────────────────────────────┐
              │                       真并发（worker=3）                 │
              ▼                                                         ▼
      A 路：英文转录                                              B 路：中文翻译
      TRANSCRIBE_EN / md/path_a.json                              TRANSLATE_ZH / md/path_b.json
      （页序串行：前缀缓存）                                        （页序串行：前缀缓存）
              │                                                         │
              │ breaks_a（英文锚点）                                     │ breaks_b（中文锚点）
              ▼                                                         ▼
      按 A 锚点分块 → chunk(road=a, :en)                        按 B 锚点分块 → chunk(road=b, :zh)
      └──────────── 公式 / 图 / 表 两路共用（road=shared, :any|:zh|:en）────────────┘
              │                                                         │
              ▼                                                         ▼
      UNDERSTAND_A（技术解剖）                                    UNDERSTAND_B（阅读地图 + 相关概念）
      引用自己的短码：来源 Chunk: A012                            引用自己的短码：来源 Chunk: B023
              └────────────────────────┬────────────────────────────────┘
                                       ▼
                       前端统一展示：阅读器 / 理解页 / 知识库 / 学习
```

**阅读器里的行是两路产物的合并结果**（第三步，与理解并行不冲突）：

```
A 侧输出块 ──src="b03|b04"──┐                 ┌── 按块号交格（lattice）逐块走
                            ├── 合并 → rows ───┤   任一侧的块已在本行 → 并入（1:N 合成一行）
B 侧输出块 ──src="b03"/"b04"┘                 └── 只有一侧有主 → 并入，绝不新开一行错位
```

## 2. 两路并发（需求①）

| 项 | 实现 |
|---|---|
| 任务 | `POST /papers/{id}/translate` 的 `path` 取 `a` / `b` / `fused`，**每路一个任务**（幂等：同类进行中任务直接复用） |
| 并发 | `task_worker_count = 3` → 两路真并发跑；同一路内部**页序串行**（这是前缀缓存成立的前提，见 §7） |
| 模型 | 每路各自的 provider / model（`translation_service._path_provider` / `_current_model_id`） |
| 产物 | A → `md/path_a.json`（`original_md` / `breaks` / `src`）；B → `md/path_b.json`（`translation_md` / `breaks` / `src`）；`fused` → `md/pages.json`（对照臂，保留） |
| 事件 | A 路发 `page_transcribed`（写 `transcribe_done`），B 路/融合发 `page_translated`（带 `path`） |
| 进度 | 任务面板 = 本任务口径（`scope_total`，支持"只重跑几页"）；论文卡片 = 全篇口径（`done/total`） |

实测（强制全量重跑，`data/logs/snapshot/two-path-run-p4b-final.json`）：

| 论文 | 页数 | A 路 | B 路 | 失败 |
|---|---|---|---|---|
| turboquant | 22 | 22/22，432s | 22/22，392s | 0 |
| attention | 15 | 15/15，248s | 15/15，390s | 0 |

两路耗时同量级、互不等待 —— 并发是**真的**（不是"依次跑两遍然后对外说并发"）。

## 3. 两路各自分块（需求②③）

### 3.1 chunk 记号（marker）

一条 chunk 的**身份、位置、类型**三件事全部落在 id + `metadata_json` 里（不改表结构）：

| 记号 | 取值 | 说明 |
|---|---|---|
| `id` | `{paper}:{A\|B\|空}:{type}:{first_row_id}[-{last_row_id}]` | **路号进 id**：两路的划分本来就可能不同，id 撞在一起会出现"同一条 id 指两份内容" |
| `chunk_type` | `text` / `unit` / `formula` / `figure` / `table` | `text` = 上下文单位；`unit` = 检索单位（`row ⊆ unit ⊆ chunk`）；公式/图/表 = 原子块 |
| `lang`（行后缀 + metadata） | `:en` / `:zh` / `:any` | A 路只出 `:en`、B 路只出 `:zh`；公式是 LaTeX → 只出 `:any`（旧实现中英各一行、正文完全相同，76 组冗余） |
| `metadata.road` | `a` / `b` / `shared`（缺省 `shared`） | `shared` = 图/表/公式（两路共用） |
| `page_no` / `block_id` / `end_block_id` / `order_global` | — | 定位回阅读器行/页 |
| `section` / `metadata.section_path` / `section_kind` | `body` / `appendix` | 附录要进库但可识别（检索侧可降权） |
| `content_hash` / `content_preview`(≤200) / `token_count` | — | 全文只在向量库（规划 §8 铁律：MySQL 不存正文） |
| `metadata.pair_id` | — | 对侧语种行（`zh` / `en` 行各指自己本体） |
| 单元专属 | `parent_chunk_id` / `prev` / `next` / `anchor_used` / `row_ids` | small-to-big 直接用，不必检索时现算 |

> ⚠️ **块号 ≠ 行号**：`src` 里的 `bNN` 是**页内解析器块号**（`p01-b01` 的短写），不是阅读器行 id。
> 阅读器行 id 形如 `p003-04`，是合并之后的产物。两套编号不要混。

### 3.2 两路边界为什么允许不同（需求②）

- **输入侧**：`breaks_a` 是英文锚点、`breaks_b` 是中文锚点，分别落在原文侧 / 译文侧
  （`chunking.is_break(row, road)` 按 `semantic_break_side` 判）；
- **装配侧**：`chunking.build(..., road="a"/"b")` **各装配一次**，各用各的锚点、各按**自己那一侧**的字数卡长度
  （中英字符数差异很大，混用会让其中一路系统性地切碎或切粗）；
- **约束只在每一路内部成立**：`row ⊆ unit ⊆ chunk`、`chunk = 整数个 unit` —— 跨路**不要求**一致。
  用户口径：两个模型对语义边界的理解可以不同，不要强制它们对齐。

### 3.3 共享坐标契约（P4b）—— 合并时的共同行格

两路各自按页图分段，块数经常差 1~2 段。只靠"结构类型 + 跨语言标记"做差分对齐有两类修不掉的毛病：
**整页错位**（多出来的那段该插在哪不可判定）与**页首分歧**（两个同级标题键完全相同）。
根因是**两侧各自分段、没有共同坐标**。

契约就是补上这个坐标 —— 用**解析器块索引**（`reader_service.load_block_index`，`turboquanton-p01-b01`，
带 `order/type/text/section`）：两路拿到的是同一份，且与本轮产物无关，是天然的共享格。

| 环节 | 做法 |
|---|---|
| 输入 | 页面正文每段印 `[bNN]`；页面 prompt **尾部**再给一份块清单 + `src` 字段说明（`coords.SRC_TAIL`） |
| 输出 | 模型除 `original_md`/`translation_md`/`breaks` 外再给 `src`：**与输出块一一对应、按顺序**，每项写它覆盖的块号（`"b03"` / `"b03|b04"` / 同一块号出现两次 = 一个块拆成两块） |
| 校验 | `coords.validate_src`：项数 == 输出块数；块号都在本页；合起来**恰好覆盖每个块一次**；顺序单调。**任一条不满足 → 这一页退回 `pair_rows`** |
| 合并 | `coords.pair_rows_by_src`：在两侧划分的交上走块号 —— 某块号只有一侧有主 → 并入当前行；主块已在当前行 → 并入（**这就是 1:N 合并**）；否则开新行。行内容 = 该侧各块 Markdown 依次拼接，**不重复** |
| 落模型 | `reader_service._merge_page`：两侧都有 `src` 且合并出非空行 → 用坐标行（`align="coords"`），否则退回 `pair_rows` |

**为什么这么放（缓存安全，见 §7）**：契约与 `[bNN]` 全部落在页面 prompt 的**前半段之后的尾部**，
而下一页 prompt 的公共前缀 = `system + 简报 + 骨架 + previous(1..N-1) + 本页输出`，逐字节不变。
唯一动过的是**首轮**把 `src` 写进了 system prompt 的字段清单（实测采纳率 5% → 64%，代价 ≈1.3% 的 prompt token）。

### 3.4 已修的回归：坐标合并会丢标题的 `level` / `number`（P9）

P4b 上线后实测发现一个**读者看得见**的副作用：`pair_rows_by_src` 造行时只带
`original / translation / type`，而 `pair_rows` 还会带 `level` / `number`。于是**走坐标合并的页
（turbo 9/22）所有标题行都缺这两个字段**，两个下游同时中招：

| 下游 | 症状 |
|---|---|
| `reader_service.build_outline` | 它只收 `level` 在 1..4 的标题行 → 这些标题**从目录里静默消失**：`# B MATHEMATICAL PRELIMINARIES`、`## B.1 SHANNON LOWER BOUND…`、`## C.1`、`## C.2`、以及正文页上的若干标题（目录 21 → **24** 条） |
| `chunking.section_tree` → 归节 | 分块层按"标题行在它之前、层级最深"归节 → p16 整页被算进 `REFERENCES`，公式块的 `section` 也跟着错 |

后果是 `q16`（附录 B.1 的 Shannon 下界）在**公式专项**检索里判 `matched=false` ——
看起来像检索退化，其实是**章节归属错了**。

**修法**（`coords.pair_rows_by_src`）：与 `pair_rows` 逐字一致地取"优先 A 侧"的
`level` / `number` 搬到行上；`tests/test_two_path_coords.py` 加一条回归断言。
**不需要重跑模型**（`level` / `number` 是读时从已落盘的 Markdown 算的），但**需要重建索引**
（chunk 的 `section` 是建索引时定的）：turbo 314 → 352 行、attention 137 → 160 行。
实测收益见 §8 的回归表（公式专项 90.9% → 100%，MRR 0.9611 → 0.9833）。

## 4. 第二阶段「理解」（需求④⑤⑥⑦⑧）

### 4.1 为什么必须是第二阶段（需求⑤）

理解读的是**已经落库的 chunk**（不是页图、也不是原始解析文本）—— 所以"理解结果引用了哪一段"
与知识库检索用的是**同一套 chunk id**（需求④：chunk 是引用的基准单位）。

提示词完全分开：`understanding/prompts.py` 的 `UNDERSTAND_A_SYSTEM` / `UNDERSTAND_B_SYSTEM`，
**不复用** `TRANSCRIBE_SYSTEM` / `TRANSLATE_SYSTEM`。把理解塞进翻译提示词会让翻译同时干两件事、两边都变差。

任务侧是两个独立任务（`UNDERSTAND_A` / `UNDERSTAND_B`，与页级翻译同构：幂等 / 取消 / 面板分得清）：

```
POST /papers/{id}/understand  {"paths":["a","b"],"force":false}  → 两路各一个任务
```

### 4.2 两路做不同的事（需求⑥⑦）

> **2026-09-26 调整**（用户看过真实结果之后的口径）：A 路原先是"技术解剖"，用户判定它**与阅读地图重复**
> （两边都在讲方法链条与实验），于是换成 **论文精读框架**，并把用户点名要的**论文创新点放在这一路**
> （它要覆盖的方面比 B 少，放得下）。同时确认：**前端不暴露"两路"这个概念**，两路产物在前端拼成一篇
> （论文精读 + 相关概念 + 怎么读这篇论文），所以提示词里也不写"你是 A 路 / B 路"。

| | A 路（英文转录侧） | B 路（中文翻译侧） |
|---|---|---|
| 角色 | 很会带人读论文的老师 | 很会带人读论文的老师 |
| 产出 | **论文精读**：基本信息 / 背景与问题 / 动机与 gap / **贡献与创新点（逐条对照已有工作）** / 方法 / 实验 / 结论、局限与启发 /（可选）复现要点 | **阅读地图**：一句话概括 / **相关概念（放在最前，定位是"补充的相关知识"）** / 推荐阅读顺序 / 读前须知 / 难点 / 与其他工作的关系 |
| 材料 | 本路 + 共用的 `unit/formula/figure/table`，只取 `en` 与 `any` 行 | 同上，只取 `zh` 与 `any` 行 |
| 短码 | `A001…` | `B001…` |

**论文创新点写在 A 路**（用户口径："论文创新点放在任务少的那一路"）：提示词要求**逐条**写清贡献，
并且每条都要说明"相对已有工作**新在哪**"，专门禁止"把'我们提出了 X'照抄一遍"。
**相关概念写在 B 路**（需求⑧），它的定位是**补充的相关知识** —— 读懂这篇论文真正需要、
但论文本身不一定讲清楚的概念（可以超出论文：教科书常识、同方向背景都行），仍必须引用本路短码。

实测（新提示词，2026-09-26）：

| 论文 | A 路（论文精读） | A 路的创新点小节 | B 路（阅读地图 + 相关概念） |
|---|---|---|---|
| turboquant | 12563 字 / 130 引用 | 「3. 贡献与创新点（逐条对照已有工作）」 | 7132 字 / 86 引用 / 8 个概念（Voronoi 剖分、Lloyd 码本、两阶段残差量化…） |
| attention | 7100 字 / 72 引用 | 「贡献与创新点」 | 4529 字 / 47 引用 / 8 个概念（自注意力、缩放点积、多头、位置编码…） |

**结果不是固定 schema**（需求⑦）：Markdown 部分原样保留，模型增删合并小节都合法，
系统只约定"要覆盖哪些**方面**"，不约定小节标题与数量。提示词里明写"不要套固定模板"。

材料清单（`chunk_inventory`）**只给短码 + 220 字预览**（`PREVIEW_CHARS`）：理解要的是"看懂了再讲"，
把全文塞进去只会让它抄原文。上限 `MAX_ITEMS=420`。

### 4.3 短码与引用校验（需求④）

- 模型引 `A012` 这种短码（引用 `turboquant-…:b:unit:p006-04-p006-06:zh` 不现实：太长、抄错一个字符就没法校验）；
  B 路的写法与用户给的例子一致：`（来源 Chunk: B023）`。
- 落库时把短码解析回真正的 chunk id，**短码映射跟结果一起落库**（`inventory` 一列），
  所以"下次重建索引换了编号"不会让已有解读自我矛盾。
- 校验只查引用：跨路引用、不存在的短码 → `invalid_refs` / `cross_road_refs` + `refs_ok=false`。
  **不丢结果**（理解内容本身仍然有用），前端明确标"引用不可信"。
- B 路硬要求（需求⑧）："相关概念"那一节里必须有本路短码，否则 `missing_concept_refs=true`。

失败与重试（实测踩到的两个坑，都已在代码里处理）：

| 现象 | 处理 |
|---|---|
| 思考模式吃光预算、正文为空（A 路第一次：reasoning 8000、`finish=length`） | `_generate` 按 `MAX_TOKENS=12000` 起，用页级流水线同一套 `_escalate_max_tokens` 升档，最多 3 次 |
| 输出被长度截断，没写收尾 JSON（B 路第一次只写了 4 节，"相关概念"整节没出来） | 没有收尾 JSON → 视为截断，`max_tokens ×2` 有界重试一次；同时把"相关概念"提到 B 路**最前面** |

### 4.4 概念：B 路产出、读时投影（需求⑧⑩）

`parse_concepts(markdown, by_code)` **在读时**从 B 路自由 Markdown 里投影出结构化概念
（「相关概念/核心概念」小节 → 到下一个同级或更高级标题为止 → `##`~`####` 子标题即概念，
标题里的中英文名用 `_split_concept_name` 拆开，正文里的 `Bxxx` 短码归到该概念）。

为什么不生成时落库：理解结果是自由 Markdown（需求⑦），"概念"是**投影**而不是事实源；
读时投影的额外好处是**不改表、不用重新生成** —— 已经存好的解读立刻就能出概念列表。

`GET /papers/{id}/related?page=N&tolerance=1`：概念的引用里有 chunk 落在 `[N-1, N+1]` 内即命中
（引用的单元常常跨页，完全等值会漏掉大量"其实就在这一页"的概念）。
**这个接口是给知识库用的**（"读到这一页时相关的知识"），**阅读器不再调用它**（用户口径，见 §5）。

## 5. 前端统一展示（需求⑨⑩⑪）

| 面 | 路由 / 入口 | 内容 |
|---|---|---|
| 阅读 | `/reader/:paperId` | 左栏 8 个页签：`toc / search / annotations / formulas / figures / terms / tasks / **insight**`；`insight`（解读）= 一份解读（论文精读 + 相关概念 + 怎么读这篇论文），右上角一枚图标按钮到整页版 |
| 理解 | `/understand/:paperId` | 与悬浮面板**同一套三块结构**（论文精读 / 相关概念 / 怎么读这篇论文）、**不暴露两路**、引用只做标注、未解读时「开始解读」→ 起任务 → 轮询 |
| 知识库 | `/knowledge` | chunk 浏览 + 语义检索（`/rag/similar`，`scope:'paper'` 只查本文）+ RAG 问答 |
| 学习 | `/study` | 占位（下一阶段） |

### 5.1 「解读」的九条交互（2026-09-27 第二轮定稿，需求⑩）

> 这一节改过两版：第一版把解读做成**右侧悬浮面板**（不挤压正文），用户看过之后要求
> **放回左侧栏、与阅读地图共用一个页签**，并补了"新标签页打开"按钮、侧栏宽度按模式给上限、

5. **「当前页相关」整条链路移除**：阅读器不再调 `/related`，没有徽章、没有置顶。
   该接口**留给知识库**（"读到这一页时相关的知识"）—— 见 §4.4。

   `POST /papers/{id}/understand {paths:['a','b'],force:true}`；**已有解读时先弹原生 confirm**；
   没建索引时**原样**显示后端 400 文案（"这篇论文还没有可理解的 chunk：先建索引（知识库页）再来理解"）。
   论文库原来那个**「重新解析」按钮已删除**（解析仍可在"未解析论文点翻译"时由后端自动串起来）——
   这就是"(转录+翻译) 与解读**解耦**"：解读有自己独立的重新生成入口，不再和解析绑在一起。
7. **左栏宽度按模式给上限**：下限 220px；**对照模式（`view_mode=bilingual`）上限 360px**、
   **非对照上限 640px 且不超过视口 60%**；切换模式 / 窗口 resize / 双击复位 / 拖拽实时夹取
   **走同一个 `clampAsideWidth`**（不在某一条路径上漏夹）。**点「解读」自动变宽到 520px**
   （按当前上限夹取，且**只增不减** —— 用户手动拖宽过就不缩回去；对照模式下会被夹到 360，
   因为那时正文本来只剩半屏）。
8. **文本对照模式下表格行左右并排**：`textCompare`（对照 + 两端都是文本、没有原 PDF）里
   `.wide`（`type=table`）行**继续走两列网格**，两端各自占一列 —— 之前那条
   `.pg-rows.two-col .row-pair.wide { display: block }` 会把原文表放上面、译文表放下面
   （用户口径："分开显示而不是上下显示"），已改成两列 + **每列自己横向滚动**；
   插图（`.row-figure`）仍是通栏，不动。
9. **左栏「任务」页签按类型一行 + 进度条**：`翻译 / 转录 / 解读 / 索引 / 解析` + 状态徽章
   （已完成 / 进行中 / 排队中 / 已暂停 / 已失败 / 已取消）；**有进度可算时显示进度条**
   （`total>1`，或有 0~100 的 `progress`）；**已完成的行只显示"已完成"徽章 + 满格条、不显示
   `done/total` 数字** —— 后端确实存在 `done=1/total=3` 却 `completed` 的任务，
   把数字摆出来会让人以为出错。在跑的行给「取消」。

搜索页新增「关键词 / 语义」分段：语义模式走 `POST /rag/similar {query, paper_id, scope:'paper', top_k:8}`。

## 7. 缓存与失效

DeepSeek 的自动前缀缓存是**最长公共前缀、块粒度**的。页级 prompt 的结构刻意做成：

```
[system][稳定前缀：简报+术语表+全文标题骨架][previous：第 1..N-1 页的模型输出][本页输出]
 └── 全篇不变 ──┘└──── 逐页追加、表头不带页码 ────┘└ 尾部内容不在下一页的公共前缀里 ──┘
 └──────────────────────── 下一页的公共前缀 = 这一整段，逐字节不变 ────────────────────────┘
```

- 前文（`history_context`）来自 **store 里已落盘的模型输出**，不是 prompt 里的页面正文 ——
  所以页面正文/尾部的任何编辑都**不影响**下一页的公共前缀；
- 因此 `src` 契约、`[bNN]`、块清单全部放在**页面级**（`{body}` 与尾部），**不动 system prompt、不动稳定前缀**；
- 唯一付过代价的一次：把 `src` 写进 system prompt 的字段清单（采纳率 5% → 64%），实测第一页失去命中
  （prompt 6025 / 命中 4480），第 3、6 页恢复到 7808/7978 与 10752/10905 —— 约 1.3% 的 prompt token。

**没有**"前缀变了就作废产物"的逻辑（`prefix_sha` 是没人读的死变量，已删）。缓存是**省钱优化**，不是正确性依赖。

**重翻译不影响已有解读**：重新翻译 + 重建索引后旧 chunk id 会失效，`split_live_refs` 把引用分成
"还能跳到原文"与"已过期"，**过期的保留**（页码来自生成时的 inventory，照样能跳）另列 `stale_refs`
让前端标一句"引用已过期（论文已重新翻译）"。丢掉它等于"重翻译一次就把解读打回原形"。

## 8. 不变量与验收

| 层 | 不变量 | 落点 |
|---|---|---|
| 分块（每路内部） | 行覆盖恰好一次；顺序不交叉；不跨不可比节；本路文本 ≤ `hard`；正文块里不出现表体/图注/参考文献行；单元按行序恰好一次覆盖、每条单元恰属一个父块、邻居同父相邻、≤ `unit_max_chars` | `chunking.validate` |
| 坐标契约 | 项数 == 输出块数；块号只取本页；恰好覆盖一次；顺序单调 | `coords.validate_src`（失败即整页回退） |
| 理解 | 只允许本路短码；B 路概念节必须有引用；不按 schema 校验 | `understanding.validate_refs` / `concept_sections_missing_refs` |
| 并发/任务 | 同类进行中任务复用；进度口径（任务 vs 论文卡片）分开 | `task_service` |
