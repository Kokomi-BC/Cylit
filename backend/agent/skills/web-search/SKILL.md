# 联网搜索与读原文

两个工具永远可用：`web_search`（搜）+ `web_fetch`（读某一篇的正文）。
它们查的是**公开网页**，不是本地的论文库。

## 什么时候用

- 问题问的是论文**外面**的事：某个方法的官方文档 / 开源实现 / 数据集在哪、
  这篇论文是否已发表或在哪个会议、某个库现在的版本与用法、最近有没有更新。
- 用户明确让你"上网查一下 / 搜一下 / 看看这个链接"。
- 论文里引用了某个工具或数据集，用户想知道它现在怎么样。

## 什么时候别用

- **论文内部的问题优先 paper_search / kb_search**："这篇怎么写的 / 它为什么这么做 /
  实验数字是多少"，答案只能来自论文里的材料；网页里的二手解读不能当论文的论断。
- 别用搜索代替读论文：先在论文里找，找不到再补外部信息。
- 别为了"看起来完整"顺手搜一遍：搜到的每条都要在答案里被用到，否则就是白花钱。

## 搜索语法（原样传给搜索引擎）

- **限站**：`site:arxiv.org`、`site:github.com`；多个站点用 `OR` 连接：
  `site:github.com OR site:huggingface.co`。
- **排除站点**：`-site:csdn.net`（内容农场多，值得排掉），多个用空格分隔。
- **精确短语**：`"random rotation"` 加引号；排除短语写 `-"release notes"`。
- **时间**：`after:2025-01-01` / `before:2026`（查"最新进展"时很有用）。
- 一次只查一件事。几个问题塞进一个 query，结果一定又稀又偏。

## count 怎么填

- 默认 **8** 够用：一般 3~5 条就能定位到官方文档。
- 想"扫一遍都有谁在说"可以给到 **10~20**；超过 20 通常只是在读同一批内容的不同镜像。
- 上限 50（官方限制），超出会被拒绝。不是越多越好：条数多只影响账单和上下文，不影响质量。

## 什么时候值得 web_fetch

只有这三种情况才去读原文（正文很占上下文，抓五篇等于把前面的材料全挤掉）：

1. 摘要里已经看到你要的那句话，但需要**完整的上下文或数字**才能引用；
2. 用户给了链接，或明确问"这页怎么说的"；
3. 摘要互相矛盾，需要看原文判断。

**不要**抓搜索结果页、站点首页、要登录的地址（会报抓不到）。
正文被截断（返回里 `truncated=true`）且关键内容在后面时，调大 `max_chars` 再抓一次。

## 答案怎么写

- 引用网页必须给 **markdown 链接 + 站点名**，例如：
  `[DeepSeek 官方文档](https://api-docs.deepseek.com/…) · DeepSeek API Docs`。
  只写域名、只写"我看到网上说"都不行 —— 用户要能点过去自己核对。
- 说清**哪一句来自网页、哪一句来自论文**：网页给的是外部信息，不能伪装成论文原文，
  也不要给它编 `[n]` 编号（编号只属于论文里的材料）。
- 网页之间冲突时把分歧写出来（谁说的、什么时间），不要自己挑一个当结论。

## 出错了怎么跟用户说

工具会返回一句人话的失败原因，**照它说，不要含糊过去**：

- 密钥没配 / 无效 / 过期 → 让用户去「设置 → 联网搜索」粘贴密钥并点「验证」；同时告诉用户
  "这次回答没有联网依据"。
- 频率或额度受限（429）→ 说清是调用太频繁或额度用尽，稍后再试。
- 超时 / 服务错误 → 说"这次没查成"，可以换关键词再试一次；仍失败就用已有材料回答。
- 抓不到某个网页（404）→ 说这一页打不开，换一条结果。

**任何情况下都不要凭记忆假装搜过**：没拿到结果就说没拿到。
